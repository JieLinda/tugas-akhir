## What this is

Pulse (AI Pulse) is a talent-succession-planning platform for MPM Motor. It manages positions (Position Management), pools eligible candidate employees, and runs AHP + TOPSIS scoring to rank successors against configurable program templates (e.g. Talent Pool, Critical Position programs). It is multi-tenant (Mulia / MSO / ERRO business units share one deployment).

The repo is four deployable units that share one PostgreSQL database:

| App | Path | Role |
|---|---|---|
| **web** | repo root (Next.js) | UI, server actions, orchestration |
| **sync-service** | `sync-service/` | Pulls employee/HR data from MSSQL, REST APIs, a shared folder of job-profile PDFs, and Excel into Postgres |
| **scoring-service** | `scoring-service/` | Runs AHP + TOPSIS scoring sessions (embeddings, grounded Gemini for education, LLM insight notes) as a standalone Node process |
| **topic-service** | `topic-service/` | Python (FastAPI) BERTopic job-family clustering — UMAP → HDBSCAN → c-TF-IDF over precomputed job-profile embeddings |

All commands below run from the repo root unless noted. Package manager is **pnpm** for web/scoring-service; sync-service uses npm (has its own `package-lock.json`).

```bash
# Web app (Next.js 16, React 19)
pnpm dev                # dev server
pnpm build               # production build
pnpm start                # run production build
pnpm lint                 # BROKEN: no eslint.config.* exists and eslint isn't installed. Use tsc.

# Database (Drizzle ORM, schema at lib/db/schema.ts)
pnpm db:generate           # generate a migration from schema changes

# scoring-service (cd scoring-service first)

pnpm start  # node --import tsx src/index.ts

# sync-service (cd sync-service first, uses npm)
npm run dev                     # express server with auto-reload

npx tsc --noEmit          # no `type-check` script exists despite older docs
npm run format
```

There is no test suite in this repo (no test runner configured) — verify changes by running the relevant service and exercising the flow, and by using `pnpm build` / `tsc` to catch type errors. Note `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so `pnpm build` succeeding does **not** mean the types are clean — don't rely on it as a type-check gate.

The real gate is `npx tsc --noEmit`, per deployable. **The web app has ~52 pre-existing errors**, and none of them is live app code: 32 in `lib/talent-data.ts`'s unused prototype mock arrays (only `appSummary` and its types are read), 1 in the stale demo seeder `scripts/seed.ts`, 2 for the undeclared `@types/pg` (`lib/db/index.ts`, `scripts/apply-sql.ts`), and ~17 in `sync-service/src/*`, which the web tsconfig compiles without that service's own `node_modules` (missing `express`/`mssql`/`node-cron`/`pdfjs-dist`). Treat that count as the baseline and check it hasn't grown, rather than expecting zero — and a NEW error in live code is worth reading, not just counting: the last batch cleared from this list included an audit row written without its actor, a candidate create that hit a NOT NULL violation, and two react-day-picker v10 renames that silently dropped a calendar's focus and grid styling. `sync-service` and `scoring-service` are both at zero — keep them there, and check sync-service with ITS OWN `tsc` (`cd sync-service && npx tsc --noEmit` after `npm ci`), because under the web tsconfig its real errors drown among the missing-module ones. That is exactly how a bad merge of `main` (a87b753) shipped `job-profile-sync.ts` referencing an undefined `buffer` — every scanned PDF failed with "buffer is not defined" while the job reported ✓ — and dropped the competency-table rules from the extraction prompt; both files were restored to main's resolution.

Local full-stack: `docker-compose.yml` builds all three services (web on 3360, sync/scoring internal). Each service reads its own `.env` (`.env`, `sync-service/.env`, `scoring-service/.env`); see `.env.example` at each level.

## Architecture

### Multi-tenancy

Tenants are hardcoded in `lib/tenant.ts` (`TENANTS`, matching DB seed UUIDs — Mulia/MSO/ERRO), selected via a `pulse_tenant` cookie and resolved server-side with `getCurrentTenant()` / `getCurrentTenantId()`. Nearly every DB query in `lib/*-actions.ts` filters by `tenantId`; when adding queries, always scope to the current tenant explicitly rather than relying on RLS (there is none). Adding a business unit therefore needs a code change + deploy, not just a DB row.

**Job profile documents are the one thing scoped indirectly.** `sync_job_profiles` has no tenant column; ownership lives in `job_profile_tenants` (many-to-many), assigned directly — chosen at upload time (Sinkronisasi → Job Profile) or set per document on the Job Profiles page (`setJobProfileTenantsAction`, `lib/job-profile-tenant-actions.ts`). There used to be an intermediate admin-editable folder→tenant table; it was removed (drizzle/0055) because every real folder mapped 1:1 to a tenant of the same name, so it only added a registration step for an answer already known at ingestion. The predicate is in `lib/job-profile-tenant-scope.ts`, and a document nobody has assigned yet stays visible to every tenant by design. Crucially this scopes **display and analysis only** — `scoring-service/src/ahp-topsis-engine.ts` and the embedding rebuild read the whole corpus on purpose, because a tournament may include candidates from other units and applying the scope there would drop their career/technical criteria and silently redistribute AHP weight. See `docs/job-profile-tenant-scope.md` before touching any of it.

Auth is NextAuth with a Keycloak provider (`lib/auth.ts`), but Keycloak is optional: if `KEYCLOAK_CLIENT_ID/SECRET/ISSUER` aren't set, the app runs as a single hardcoded "System User" with admin rights (`getCurrentUser()` short-circuits). When Keycloak is configured, the JWT callback fetches org data (divisions/departments/roles/isAdmin) from an external `PORTAL_API_URL` and caches it in-memory for 5 minutes.

### Data flow: sync → candidates → scoring

1. **sync-service** pulls raw HR data from MSSQL (`DB MPMDS`, `DB MPMHRGA`), a REST API (disciplinary/education/candidates, plus employee personal information — see below), a shared folder of job profile PDFs (`LOCAL_PDF_FOLDER`, LLM-extracted — despite what its README's older sections say, there is no SharePoint client), and local Excel files (HAV quadrant, MCU medical status) into Postgres tables like `employees`, `performance_appraisals`, `disciplinary_records`, `sync_job_profiles`. It's triggered by cron (`scheduler.ts`, default Monday 1am), CLI (`npm run cli -- <job>`), or HTTP (`POST /sync/*`), proxied from the web app via `app/api/sync/[...sync]`.
2. The web app's `lib/*-actions.ts` server actions read synced data and let users curate `critical_positions` (successor-relevant roles) and `candidates` (the succession pool), plus `program_templates` (scoring config: filter rules, the AHP pairwise matrix, target finalist count) under `components/governance/*`.

   **A position belongs to exactly one program** (`critical_positions.program_template_id` + `.program_code`, drizzle/0056). It is picked when the position is added and frozen as soon as the position has a scoring run — `updatePositionAction` refuses to move a scored position, because a finished ranking is an assessment made under one program's rules and re-filing it would relabel that history. Assessing the same seat under a second program means **adding the position again** with that program, which is what keeps each program's bench, filters and run history a separate list instead of stacking them on one row. Everything downstream follows from that single column: the Position Management program chips filter the position list itself (not the runs), the scoring wizard only offers positions registered under the chosen program, and `startTournamentSessionAction` rejects a run whose template does not match `positionRow.programCode`. Existing rows were backfilled from the program of their most recent run (`successor` when never scored); runs made under a different program stay attached and keep their own per-run program label.

   **Talent Pool is not a position program.** `NON_POSITION_PROGRAM_CODES` in `lib/programs.ts` holds `talent`, and `positionProgramTemplates()` is what the position form, the Position Management chips, the scoring wizard, the run-history filter and the agent's `positions.create` all select from. Talent Pool answers "who in this business unit clears the bar?" — it filters candidates and has its own menu (`/talent-pool`); it never targets a seat, so a run under it would produce a ranking nothing displays. **It is also hidden from Tata Kelola → Program Penilaian**: `app/(dashboard)/governance/page.tsx` passes `positionProgramTemplates(templates)` to the client, so the picker lists only programs that score a seat. Everything that editor configures — criteria, the AHP matrix, the finalist target, rule enforcement — has no reader for a program no run is started under, and its one live setting is now edited on the Talent Pool page. Nothing became unreachable: the template is `isSystem`, so `deleteProgramTemplateAction` already refused it. Program *labels* are still built from the FULL template list, so a position filed under a no-longer-offered program renders its real name — only the governance picker is filtered.

**The Talent Pool page now shows and edits those rules itself** (`components/talent-pool-filter-panel.tsx`, `lib/talent-pool-actions.ts`). The list on that page IS the output of the tree, and the tree lived one page away, so tuning a bar meant edit, save, navigate, count, navigate back. The panel closes that loop: the rules render above the list that obeys them, an edit previews its own effect before anything is written, and a save returns the recomputed pool so the list answers to the new rules without a reload. The preview is not a second evaluator — `getTalentPoolData` takes an optional `overrideTree`, so a previewed count and a saved one come from one code path; `ruleCount` is counted off that tree rather than the flattened `filterRules` list, which under an override is still the stored one. Editing needs `governance.manage` (the page itself only needs `candidates.view`): this template also decides who a scoring run accepts, so surfacing it must not widen who may change it, and the action refuses regardless of what the UI shows.

**Two controls are deliberately absent from that panel**, both for the same reason: they decide what a scoring RUN does with a failing candidate, and no run is ever started under `talent`. The `enforceFilterRules` switch is not offered and `updateTalentPoolFilterAction` does not write that column — a page must not move a value it never showed. Per-rule `severity` (Menggugurkan / Hanya menandai) is hidden through `showSeverity={false}` on the shared `FilterRuleEditor`/`FilterTreeView`, so a rule written here carries no `severity`, which the engine already reads as hard. Both stay in Tata Kelola, where the programs that do score are configured, and the MCU advisory rule that drizzle/0071 depends on is untouched. The page's old "Aturan filter tidak ditegakkan" banner went with them: it warned about a consequence this program cannot have.

**One control IS offered there and nowhere else: a per-rule Aktif / Nonaktif switch** (`FilterRule.enabled`; `false` = off, absent = on, so every stored rule behaves unchanged; `allowDisable` on the shared `FilterRuleEditor`). Unlike severity it changes THIS list, now. An off rule keeps its values and takes part in nothing — no verdict, no advisory flag, no "Tidak Lolos" reason — because the engine STRIPS it (`decidingFilterTree` in `lib/filter-rules.ts`, which now also owns the advisory stripping `applyProgramFilters` used to do privately) rather than evaluating it as true: a rule that always passes inside an `or` would open that `or` for everybody. Counts say "N aturan aktif · M nonaktif"; the read-only `FilterTreeView`, the run-configuration panel and the program prompt context all mark an off rule rather than rendering it as live. Tata Kelola does not offer the switch for scoring programs — the engine would honour it, but nobody asked for a rule a run silently ignores. Each rule on the Talent Pool panel also carries a note (`ruleNote`) saying what it does beyond the list — Disiplin gates Talent Mapping, HAV/PA/BA are the map's inputs, MCU only flags — and the stored advisory MCU rule's note is how the page now says that MCU-unfit people are NOT rejected there, which the hidden severity badge used to leave unsaid.

**Rules already saved on a program template can be applied from that panel** ("Terapkan dari template program", `components/talent-pool-rule-import-dialog.tsx`, merge logic pure in `lib/filter-rule-import.ts`, pinned by `pnpm test:talent-pool`). Sources come from `listTalentPoolRuleSourcesAction` (`governance.manage`), read fresh on every open: each template of the active business unit as it is saved now (Talent Pool's own first) plus the system programs' shipped defaults. The unit of choice is a TOP-LEVEL child of the source tree — a whole group or a rule, never one branch of an `or`, which would silently tighten it. Applying only replaces the DRAFT; the preview counts it and Simpan is still the only write, with the source names added to the audit line (`appliedFrom`). Three rules in the merge: "Tambahkan" AND-s beside the draft and, under an `or` root, wraps the draft as one branch instead of adding alternatives (which would LOOSEN the bar); "Ganti aturan pada bidang yang sama" removes only the draft's top-level rules on that field, never one nested in a group; and identity is field/operator/value/severity/on-off — wording is not — so an identical rule is skipped and a no-op import leaves the draft untouched. Rules are copied verbatim, so an imported advisory MCU rule stays advisory.

**Two panels were removed from that page rather than restyled.** "Nyaris lolos" (a stat card, a list filter and a per-candidate badge for failing exactly one rule) and "Aturan paling sering menggugurkan" (a rejection tally per rule, clickable as a filter) both answered *which rule to change* — a question only worth asking in order to change it, which is now possible in place. `TalentPoolData.ruleTally` is gone with the card; `blockedOnlyByMissingData` stays, because an empty column is a data-entry gap rather than an assessment outcome and still earns its own label.

**Talent Mapping (`/talent-pool/mapping`) is where a candidate's HAV is CONSOLIDATED, and every reader uses the result** (docs/talent-mapping.md). The **HAV in force** is manual placement (`talent_mapping_placements`) > HAV Excel upload (`candidates.hav_quadrant`) > formula (`deriveHavQuadrant`, PA × behaviour) > none — `resolveEffectiveHav` in `lib/hav-effective.ts` — **except that a CHANGE to PA or BA pins the formula above the upload** (`candidates.hav_auto_tier = 'formula'`, drizzle/0098, passed to the resolver as `automaticTier`; a differing HAV upload pins `'upload'` back; a pinned formula that cannot be computed falls back to the upload). The events, last one wins (2026-11): a PA/BA edit on the Kandidat form (`candidate_edit`) or its **"Hitung kuadran HAV"** button (`hav_formula`, both via `lib/hav-formula-event.ts` inside `updateCandidateAction`'s transaction) → formula; a PA or BA workbook upload, which now runs the candidate sync straight away (`pa_ba_upload`), or the candidate sync carrying CHANGED PA/BA (`candidate_sync`) → formula, over an upload too and even when the band is unchanged; a drag on the map → manual until the next PA/BA change; a HAV upload whose quadrant CHANGED, or — only for an upload made in the app — differs from the HAV in force → upload (the shared HAV.xlsx counts only changes, or every Monday would undo every PA/BA edit). Pure rules in `sync-service/src/services/hav-order.ts` (`paBaFormulaEvent`, `havUploadEvent`); demo mode mirrors it on the copy (`havTier`, `havFormulaPinnedIds`). **Apply drizzle/0098 BEFORE deploying** the three deployables (the Kandidat save writes the column; readers degrade to the static order without it). The resolver is folded into rows by `withEffectiveHav` (`lib/hav-placements.ts`), which REPLACES `havQuadrant` on the row so readers that already read that field become correct without learning a new one. Routed through it: `loadFilterableCandidates*` (every eligibility evaluation, incl. scoring pool builds), the Talent Pool loader, the profile builders, Beranda, the Job Profile Match detail — but NOT a finished run's rows: `getScoringRunResults` shows the quadrant the RUN scored (`recordedHavQuadrant` in `lib/run-score-breakdown.ts`, displayed through `runHavText`), so a placement or upload after the run never relabels its HAV score; a row without the AHP+TOPSIS record says "tidak tercatat di run" rather than borrowing today's — and, in scoring-service, the engine's candidate loader via the MIRROR `scoring-service/src/hav-effective.ts` + `hav-placements.ts`; a THIRD copy sits in `sync-service/src/services/hav-effective.ts`, and `tests/talent-mapping/hav-parity.test.ts` pins all three (exhaustive over every six-slot PA CSV). **The formula tier reaches scoring by HR's decision**, knowingly re-weighing PA + behaviour through the HAV aspect; runs record `rawInputs.havSource` and `runInfo.hav.sources` so the overlap is visible. **Between a hand placement and a sync, whichever came LAST wins, and that is decided by two DATABASE clocks** (drizzle/0080): `talent_mapping_placements.updated_at` (the move action writes ``sql`now()` ``, never `new Date()`, because it is compared against a clock the database wrote) and `candidates.hav_auto_changed_at` + `hav_auto_change_source`, moved only when a sync CHANGES the automatic HAV. Both readers — web `loadManualHavQuadrants` and scoring-service's — apply the same SQL predicate (`hav_auto_changed_at IS NULL OR p.updated_at > hav_auto_changed_at`), so they agree even if a placement and a sync race; the sync that moves the clock also deletes older placements and logs them, all in its own transaction (`sync-service/src/services/hav-supersede.ts`). The events are defined in `hav-order.ts` and pinned by `tests/talent-mapping/hav-sync-order.test.ts` (sync side: `superseded_by_upload` / `superseded_by_sync`; web side: `formula_applied` / `superseded_by_formula`, which the Riwayat HAV tab files under Manual). NOT events: an unchanged re-read (PA compared per six slots, BA case/space-insensitive), the shared HAV.xlsx restating an unchanged value, a PA/BA change TO something the formula cannot place (data vanishing must not void a decision), and — the one that is easy to get wrong — **the candidate sync re-copying an older `sync_hav` value** onto a row edited outside the sync: that upload was an event when it arrived, and stamping it at copy time let old data displace newer placements (measured: 4 Mulia rows differ from their 2026-06 `sync_hav`, one with a 2026-10 placement). Two sync changes make the clocks honest: `runFullSync` now syncs BA BEFORE the candidate step (it ran after, so a BA change reached the HAV in force a week late), and the candidate upsert COALESCEs `hav_quadrant` (a clean sync empties `sync_hav`; without it every HAV blanked and the next HAV import read every row as a change, voiding every placement). **The map's population is everyone the Talent Pool's DISCIPLINE rule admits** (`talentMappingGateTree`: the deciding tree with every non-discipline leaf replaced by TRUE — not removed, so Talent Pool ⊆ map holds for any tree shape); HAV, PA and BA are the map's inputs and MCU is advisory, so none of them gates it, and switching the discipline rule off opens the map to every live candidate. The full Talent Pool verdict rides along as information (`inTalentPool`, plus `poolQuadrants`, every square under which they would pass) so the drag and the dialog say what a move does to membership; the Talent Pool page shows the same count ("Di Talent Mapping", `TalentPoolData.mappingPopulation`). Move rules in `moveTalentMappingCandidateAction`: justification on **every** move; the candidate must be on the map; `expectedQuadrant` plus a write conditional on the stored sealed quadrant (a version token — racing moves: exactly one wins); placement + audit in one transaction; **moving onto the automatic square DELETES the placement**. A placement keeps `baseline_quadrant` + `baseline_source` (drizzle/0079) — the automatic answer it overrode — which is how drift WITHOUT a sync (a manual PA edit, a re-copied upload, a pre-clock placement) is flagged. History is the parked prototype's `talent_audit_logs` as `mapping_kind = 'hav16'` rows (`manual_place` / `revert_to_automatic` / `superseded_by_upload` / `superseded_by_sync` / `automatic_changed`) with a `changed_by_username` snapshot (`sync:hav-upload` / `sync:hav-folder` / `sync:candidates` for sync rows); the page's "Riwayat HAV" tab filters Manual / Sync. The Kandidat form's HAV field is read-only on edit and the update action never writes `hav_quadrant`; it moves the HAV only through the formula events above (the button previews the formula over the form's own PA/BA and applies it on Simpan). Note the candidate sync overwrites PA/BA with the source every run (as before), so a manual PA edit that differs from the source returns to it — itself a PA change, so the HAV follows the formula over the source value. Two vocabulary corrections came with it: the PA axis reads Low from **any D/E/C- in the last two years** and the other bands from the newest **two graded periods** (`readPerformance`), and **Q13 is STRONG** (the 5-Box category only; `HAV_GROUP_SCORES` still scores Q13 at 60). **The "Belum terpetakan" tray is a work queue, not a chip list** (`components/talent-mapping/unplaced-queue.tsx`): the people nothing places are placed BY HAND, so each row carries the evidence for it — the formula's six PA slots per year (deciding slots ringed) plus the newest PA year OUTSIDE that window, labelled as never read by the formula (the local window 2023–2025 is empty for every Mulia candidate; 48 have a 2015/2021 grade); up to three dated BA assessments, newest first; and the axis the formula can already read. Placing is a click on a 4×4 picker laid out like the map (known axis outlined, Talent-Pool-passing squares dotted) that opens the same justification dialog a drop does, so nobody drags a row from the bottom of 269 to the top of the page; the queue has its own search and evidence filters so finding one person never filters the grid. **BA history is its own table** (`sync_behavior_competency_history`, drizzle/0081): `sync_behavior_competencies` stays one row per employee because candidate-populate joins it expecting exactly that, while the MSSQL source keeps every assessment. The behaviour sync copies the newest 3 assessment DATES (`DENSE_RANK`, since one assessment can span several detail rows) through a SEPARATE query whose failure is reported and never fails the latest-BA sync, replacing per employee. Readers merge the current row back in (`mergeBehaviorHistory`, current wins its own date), because an Excel BA upload writes only the old table and an empty history must mean "latest only", not "nothing" — and when the candidate row's BA differs from the newest sync value (10 Mulia rows here, edited outside the sync), the queue says which one the formula reads. All of it joins exactly like candidate-populate: company through `sync_company_tenant_map`, NPK through `LPAD(employee_id, 5, '0')`. **The pool loaders unlock before they decrypt** (`ensureUnlocked()` in `loadTalentPoolBase`, `getCandidateTalentPoolStatus`, `loadFilterableCandidates*`): the dashboard layout unlocks on every request, but Next.js renders layout and page in PARALLEL, so the first request after a restart could decrypt sealed rows as all-null and judge them "Tidak Lolos" — measured, exactly one sealed Mulia row on the wrong side of the first call. Most other candidate loaders still rely on the layout and share that cold-start window. Pinned by `tests/talent-mapping/*.test.ts` and `scripts/verify-talent-mapping.ts [--write]`, which checks one HAV across the pool, the map, the eligibility loader and scoring-service, the population against an independent recompute of the discipline gate, both supersessions inside rolled-back transactions, and the clock rule committed-then-restored for both readers.

   **Bulk registration goes by INCUMBENT grade** (`lib/position-bulk-actions.ts`, "Tambah massal" on Position Management). `sync_positions.grade_id` is empty for essentially every row in this deployment while `sync_employees.grade_id` is populated, so the person sitting in the seat is the only available statement of its level — and it matches what an HR user means by "grade 7 and up" (7 is where MANAGER starts; 5–6 SUPERVISOR, 1–4 STAFF, per `sync_grade_levels`). A seat is judged by its most senior incumbent, the successor range follows what the PROGRAM is for — **Critical Position** (code `successor`) takes the level below the incumbent (grooming), **Emergency Position** takes the incumbent's own level plus the one above (someone who could step in today), and any other program keeps the conservative one-below-to-own span. "One level" means one level NAME (STAFF → SUPERVISOR → MANAGER → GENERAL MANAGER → DIRECTOR, `buildLevelBands`), not one grade number, because a level spans several grades (MANAGER is 7–8) and the single-position form's own range control picks level names — and unlike the single-position form the row keeps `critical_positions.position_id` — the selection came from the master position, so storing the link is what lets a re-run recognise its own rows instead of duplicating them. Optional auto-scoring starts one AHP+TOPSIS session per created position; a position whose pool comes out empty is reported and skipped rather than aborting the batch. The preview resolves each seat's job profile up front and the dialog **names the seats that have none before the batch runs** — such a run still works but scores technical and career from the incumbents' competencies instead of the JD, which is a different number under the same label, so `scoreWithoutJobProfile` makes that an explicit choice rather than something discovered in the results.

   **Re-scoring a whole program** (`rescoreProgramPositionsAction`, "Scoring Ulang" on Position Management) starts one fresh AHP+TOPSIS run per position filed under that program. It never edits or deletes an existing run — a completed ranking is the record of an assessment on a date, the same invariant the exclusion re-rank follows — so the old runs stay in each position's history. Positions already mid-run are skipped rather than double-dispatched (two runs writing into one position's history would make the loser look failed), and the same no-job-profile notice as the bulk add applies, since a JD-less re-score silently means a different technical/career basis.

   **Resetting a program's scoring** (`resetProgramScoringAction`, dialog at `components/positions-reset-scoring-dialog.tsx` — built and working, but deliberately NOT rendered on the page; render the dialog in `positions-page-client.tsx` to expose it) is the one irreversible action on Position Management: it deletes every `scoring_runs` and `tournament_sessions` row of that program's positions, and the FK cascades take `analysis_results`, `scoring_run_exclusions`, `scoring_run_pool_aspects`, `scoring_run_traces` and the runs' `chat_messages` with them. Order matters — **sessions are deleted before runs**, because a leftover `running` session is exactly what the service's orphan sweeper re-dispatches, which would score straight back into the gap. Live sessions are cancelled through the service first, since deleting rows under a running worker fails in confusing ways. One thing deliberately survives: `position_picks` (a human decision made FROM a ranking, not part of it; its `run_id` is `ON DELETE SET NULL`), unless `deletePicks` is asked for. `confirmName` must equal the program name and is checked server-side, because a guard that lives in the dialog is not a guard.

   **Scoring dispatch is capped, not queued in a table.** `SCORING_MAX_CONCURRENT` (scoring-service, default 2) bounds processing; `startSessionProcessing` refuses beyond it and the session simply stays `running` with no worker — which is precisely what the orphan sweeper already looks for, so it starts when a slot frees. That is why bulk auto-scoring needs no queue table and no open browser tab: the runner writes `analysis_results` itself, the web app's polling/finalize is only a UI convenience.

   **Starting a session and dispatching it are two facts, and the UI used to be told only the first.** `notifyScoringService` swallowed every failure with a `.catch()` at each of its five call sites, so a dead scoring service produced the same "penilaian dimulai" as a healthy one — and the wizard then polled a session nobody was working on for its full **one-hour** `MAX_POLLS`, ending on the red "Penilaian dihentikan" that means *failed*. Nothing was actually wrong: the session and run rows are committed, and the orphan sweeper (10s interval, 15s grace, plus `resumeInterruptedSessions()` at boot) claims them. It is a **queue**, and the only bug was silence. `notifyScoringService` now returns a `ScoringDispatch` (`lib/scoring-engine.ts`) instead of throwing, every start path carries it out on its result (`StartTournamentResult.dispatch`, `StartRerunResult.dispatch`, `BulkAddResult.scoringQueued`, `ProgramRescoreResult.queued`), and the wizard, the "Hitung" dialog, the rerun dialog, the bulk-add dialog and the program-rescore dialog each render it — amber, not red, with the sentence "sesinya sudah tersimpan, jangan jalankan ulang", because re-running is exactly what a user does to a batch that looks failed and it only stacks a second session on the same seat.

   **`status` and `reason` are separate on purpose.** The UI branches on `status` (`dispatched` / `queued`) while the wording follows `reason`: a service that *answers* with an HTTP error is alive, so reporting "layanan tidak merespons" would send the operator to check a healthy process. `unreachable` covers the fetch throwing — connection refused, DNS, and the 5s `AbortController` timeout — and is the only case where "wait" is the whole advice; `rejected` (non-2xx) keeps the status code and says to report it; `unconfigured` is a missing `SCORING_SERVICE_URL`. All three are `queued` rather than a thrown error, because the rows are already committed and throwing after the commit would leave an orphan session *and* an error message. **A 404 from `/start` is never "wait"** (`describeStart404`): the web app calls it only after committing, so `{error: "Session not found"}` means the service reads a DIFFERENT database (its sweeper sweeps that one too, so the session never runs) and the reply carries the service's `host:port/db` + env source for comparison; any other 404 body means `SCORING_SERVICE_URL` reaches something that is not the scoring service. scoring-service now resolves `DATABASE_URL` before `POSTGRES_URL`, the same order as `lib/db/index.ts` — it was reversed, so an environment with both names set to different values split the two deployables silently — and warns at boot on a conflict or the built-in localhost default.

   **Position Management flags seats with no job profile.** `getJobProfileByPosition` (lib/pulse-data.ts) resolves the JD for a whole page in three set-based queries — incumbent pairing, then master position code, then title — mirroring `resolveJobProfileIdentifier`'s precedence without calling it once per row (its title tier re-reads the entire completed profile list, which is fine once and wasteful twenty times). A null answer earns a "Tanpa job profile" badge, because such a position scores technical and career from its incumbents' competencies rather than the job's stated demands.

   **Position Management shows three states the rows would otherwise hide.** A seat whose job profile does not resolve gets a "Tanpa job profile" badge; a seat scored with nobody chosen gets "Belum ada suksesor dipilih" (a ranking exists and the decision it exists for has not been made); and a holder at or past their level's retirement age gets a badge **naming them**, because a count alone sends the reader hunting. The retirement thresholds live in `lib/retirement-config.json` (50 for STAFF/SUPERVISOR/MANAGER, 55 for GENERAL MANAGER and up), read via `readFileSync` like the readiness config so an edit needs no redeploy. Its editor in Tata Kelola → Readiness is HIDDEN, not deleted (`RETIREMENT_EDITOR_VISIBLE = false` in `components/governance/governance-client.tsx`; the tab reads "Kesiapan" meanwhile) — the thresholds still apply, edit the JSON or flip the flag. A holder with no synced birth date is never flagged — an unknown is not a finding. The list also replaced its "Top Candidate" preview with **RTC**, the count of successors actually chosen: the top-ranked person is an output of the last run, while a bench is only real once somebody picks.

   **A position can have several sitting incumbents** (`critical_position_holders`, drizzle/0058). Non-unique roles (SALESMAN, INSTRUCTOR, branch supervisors) are held by many people at once; the picker used to name one and label the rest "(+N pejabat aktif lainnya)", which left them neither shown on the position nor excluded from its own pool — a sitting holder could be ranked as their own successor. `critical_positions.holder_name`/`holder_employee_id` remain as the **primary** holder because ~8 readers join on that pair (job-profile suggestion, position→family mapping, progress-running, run dossiers); the child table holds the full set. `resolveHoldersForPositionAction` offers every active incumbent in the form, `loadPositionRow` attaches them so all four pool-building paths exclude every one of them, and `searchAddableCandidatesAction` takes `excludeEmployeeIds` (plural) for the same reason.
3. **Starting a scoring run** (`lib/scoring-engine.ts: startTournamentSessionAction` — the name is historical) builds a candidate pool filtered by grade range and incumbent-exclusion and creates a `tournament_sessions` row (the whole pool in `current_pool`; `pending_pool` is always `[]`) plus a placeholder `scoring_runs` row. It then POSTs to `scoring-service` (`SCORING_SERVICE_URL`) to kick off async processing — this is fire-and-forget/best-effort; the session persists in Postgres either way and the service can resume it.
4. **scoring-service** (`scoring-service/src/runner.ts` → `ahp-topsis-engine.ts`) computes the run, mutating `tournament_sessions`/`scoring_runs` directly as it progresses. It is a separate process because one run is minutes of embedding, grounded-Gemini and insight-writer calls, which would exceed Next.js server-action/serverless timeouts.
5. The web app polls session status (`app/api/tournament/[sessionId]/status`, `components/scoring/scoring-wizard.tsx`; the route path is historical). When polling gives up, `finalizeTournamentAction` calls `POST /api/scoring/:sessionId/finalize`, which re-runs the (idempotent) AHP engine for that session.
6. **The scoring method — AHP + TOPSIS** (`tournament_sessions.scoring_method = 'ahp_topsis'`, run/result `method = 'AHP_TOPSIS'`), the ONLY method (the LLM "AI Tournament" was deleted — see below). `scoring-service/src/ahp-topsis-engine.ts` computes six aspect scores (technical via Hungarian one-to-one competency assignment over cumulative level embeddings, matched in two stages — identity (same kamus code, or same name when neither side has a code) settled BEFORE Hungarian and removed from its matrix, then Hungarian over the remainder; each cell `sim′ × levelFactor` — see `scoring-service/README.md` § "Matching runs in two stages"; career relevance = accumulated relevant experience — job-profile document similarity rescaled by corpus-measured anchors × tenure, saturating on both a years axis and a stint-count axis against a pool-derived target; behavior paired ordinal categorization 6..0; PA absolute-solution dynamic TOPSIS with all-A/all-D anchors and AHP-derived period weights; HAV 5-tier quadrant rule; education via deterministic exact-match then grounded Gemini) then ranks with AHP weights (pairwise matrix at `program_templates.ahp_config`, edited in governance via `components/governance/governance-ahp-editor.tsx`; math in `lib/ahp.ts` + a synced copy at `scoring-service/src/ahp.ts`) and classic TOPSIS. Progress is reported through `tournament_sessions.final_ranked` (`ahpProgress`), not `stages`. See `scoring-service/README.md` for details.

   **Excluding candidates from a finished run is a MARK, nothing more** (`setRunExclusionAction`, `scoring_run_exclusions`, labelled "Ditandai dikecualikan (tidak memengaruhi angka)" + reason; undoing a mark needs a reason too, and both are audited; picking a marked candidate as successor asks for an extra confirmation). The run's numbers are never touched — a completed ranking is the record of an assessment on a date — so the row is struck through and the derived counts skip it. There is no re-rank behind it any more: the `rerank` flag, `createExclusionRerank` and `rerunScoringExcludingCandidatesAction` are gone, because a ranking without somebody was a derived run whose only change was a NARROWER alternative set, and re-running is now one operation (below). Runs re-ranked that way keep `rerun_mode = 'exclude'` and still render.

   **Adding candidates to a finished run ("Tambah Kandidat Pembanding") carries the parent's WHOLE scored pool**, recovered from `scoring_run_pool_aspects`. TOPSIS is set-relative at the column norms AND the ideal/anti-ideal, and a top-N slice is uniformly high-scoring on exactly the criteria the cut was made with, so ranking only the finalists reorders carried-over candidates with nothing added at all (measured on the IT Application Development Department Head run: up to **4 places**, behavior 32.8% → 18.5% of the discriminating spread). A parent with no pool snapshot is therefore REFUSED rather than degraded to its finalists — make a new root from the wizard instead. **What a child LISTS (FR-RR-09, `composeChildResultList`)**: the union, without duplicates and ordered by the new rank, of the top N by the new ranking (N = the PARENT's finalist count — it is no longer grown by the number of comparison candidates, which used to pull in people nobody asked about just because the quota rose), every parent finalist (a displaced finalist must stay in view), and every accepted comparison candidate (the forum's question is "what about X?", so X is listed even at "37th of 60"). Each row carries its **whole-pool** rank (`analysis_results.rank` is that rank, not the row index, or "23rd of 24" would render as "#12") and a marker: comparison candidate, entered the top N, or left the top N. `is_finalist` in `scoring_run_pool_aspects` still means *made the cut*. **A new candidate is judged by the parent's rules by Tabel 2.4 category** (`classifyAgainstParent`): Rejected (discipline, PA, HAV, BA) is REFUSED and comes back in `skipped` with the rules it failed; Excluded (grade outside the seat's range) is accepted only after a per-candidate confirmation, then recorded in `filterSummary.forceIncluded` with the rule and badged "Di luar rentang grade" wherever it renders; Reconsidered (MCU fit with note, an advisory rule) is scored normally. This replaced "every new candidate is force-included whatever it failed"; the parent's own force-included entries are still inherited.

   **The full-pool "Scoring ulang dengan data terbaru" (`rerunScoringFullPoolAction`) and the other refresh modes are gone.** Newer data or a newer configuration is a new ROOT — the wizard, or "Scoring Ulang" for a program — never a child, because a child that re-reads anything live answers two questions at once. Runs created under `refresh_add` / `finalists_rematch` / `refresh_full` keep their mode and render as *mode lama*.

   **Exact ties break deterministically.** `loadAhpCandidates` is `ORDER BY id` and the closeness sort has an explicit `id` tiebreak — arbitrary on purpose, since inventing a seventh criterion would hide a decision the run never made; real ties are broken by the recorded manual tie-order control on the position page. (Two other things derived runs used to get wrong — behavior/PA/HAV read live while the other three were frozen, and the AHP matrix re-read while the snapshot was inherited — are subsumed by the full freeze below.)

   **A grounded education answer is reused across runs of one position when the question is identical** (`scoring-service/src/education-reuse.ts`, `AHP_EDUCATION_REUSE`, default on). Before calling Gemini for a candidate, `scoreEducationAspect` reads the LAST completed AHP+TOPSIS run of the same position (same `is_demo`, from `scoring_run_pool_aspects.details.educationEval`) and reuses that run's model answer when the `inputKey` matches. The key is sha256 over the EXACT system + user prompt the model is sent (built by the one `buildEducationUserPrompt` both use) minus the candidate's name, plus model / grounding / temperature / topP — so it covers education + major and the requirement as asked, AND title, job purpose, the first 10 responsibilities + indicators and the prompt, because a re-extracted JD or an edited prompt makes the old answer a reply to a different question. What is reused is the model's ANSWER (two rubric numbers, reason, queries, sources); the level axis is recomposed with this run's rule. Exact matches are recomputed (deterministic), failures (`none`) are never reused, runs from before keys existed are asked once more, and a failed read of the previous run is logged and costs calls, never the run. Provenance is on the evaluation (`reusedFrom.answeredInRunId` names the run where the model really spoke, through chains) and per run in `run_info.education.reuse`; the UI badges it "Jawaban model dipakai ulang". Pinned by `scoring-service/test/education-reuse.test.ts` (TC-EDU-REUSE).

   **Run-level diagnostics live on the RUN, not on the session** (`scoring_runs.run_info`, drizzle/0065). `runInfo` — reference-set provenance, the technical similarity anchors and their source, career scale/depth targets, AHP criteria dropped + effective weights, augment/exclusion summaries, scored/finalist counts — used to live only in `tournament_sessions.final_ranked`, and that was the wrong home: a session is working space (`current_pool`, `final_ranked.ahpProgress`) and legitimately transient, while a completed ranking is a permanent record. The scoring wizard deleted its own session on success, so **every run finished through it lost its entire diagnostics the instant it succeeded** — `getRunConfigurationAction` found no session, `runInfo` came back null, and the whole "Sumber Acuan & Penyesuaian" section of the Konfigurasi tab, the AHP dropped-criteria list, the pool counts, and the exclusion re-rank's inheritance of its base run's diagnostics all silently stopped working. The wizard no longer deletes (a `completed` session is inert: every mid-run check filters on `running`/`finalizing`, the orphan sweeper only sweeps `running`, and auto-resume handles `completed`), and the engine now writes `runInfo` to both places. Every reader COALESCEs run-first, session-second; runs whose session was already deleted have neither, and that data is unrecoverable.

**Re-running a finished run is ONE mode: `incremental_add`, "Tambah Kandidat Pembanding"** (`lib/rerun-modes.ts` — `CREATABLE_RERUN_MODES` / `LEGACY_RERUN_MODES`; decisions in `lib/rerun-freeze.ts`; one server action `startRerunAction`; the engine side in `scoring-service/src/rerun-freeze.ts`). The rules are in "Re-run scoring — aturan desain" below; the state before is in `docs/rerun-modes-inventory.md`. What the code does:

- **Apply drizzle/0086 before deploying the web app**: the Drizzle schema now selects `scoring_runs.rerun_reason`, so every `select().from(scoringRuns)` fails on a database without the column (the run tree reads it through `to_jsonb` and survives either way). **Apply drizzle/0087 AFTER the new scoring-service is running**: its triggers refuse every change to a completed run, its pool rows and its result rows (I-1), and the OLD engine wrote `run_info` and `config_snapshot.rerun.frozen` after `status = 'completed'` — those writes would now be refused (logged, run left without diagnostics). The new engine writes `completed` LAST. Deliberate exceptions in the guard: `analysis_results.manual_rank` (tie order, a human marker), FK `SET NULL`s, and INSERTs into `analysis_results` (the LLM engine still inserts results after marking completed — out of scope, left working).
- **Validated on the server**, never only in the dialog (`validateRerunRequest`): mode must be `incremental_add`; the parent must be in this tenant, `completed`, AHP+TOPSIS, and have a pool snapshot; at least one candidate; `rerun_reason` ("Alasan / permintaan forum", drizzle/0086) non-empty and at most 1,000 characters. On an ineligible run the button is rendered DISABLED with the validator's reason beside it (`getRerunPreviewAction`), not hidden. Identical requests within two minutes create one run (request key + transaction advisory lock).
- **Every picked person is classified** (`classifyRerunCandidates` → `classifyAgainstParent`, the SAME function for the dialog's preview, the candidate search and the submit, so a preview cannot disagree with the result): `new` (not in the parent's pool — the ONLY people whose six aspects are computed), `existing_pool` (in the pool but below its cut — carried with the parent's aspects, NOT re-scored, but given a row; this deliberately changed the old "1a" behaviour, which re-scored them on today's data), `needs_confirmation` (grade out of range), or `skipped` with a reason (parent finalist, not found, soft-deleted, incumbent of the seat, failed a Rejected rule, outside the parent's business units). Skipped people come back in the response and are stored in `config_snapshot.rerun.skipped` and shown in the child's banner — nobody disappears silently — and a request with nobody left is refused. The candidate search (`searchRerunCandidatesAction`: name or NPK, plus unit/position/department/grade/job-family filters) is limited to the business units the parent covered.
- **Everything else is inherited** (`resolveFrozenBasis` → `AhpRerunSpec.frozen`): program / position / level range / filter snapshot (`programTemplateId` can no longer be passed at all), the parent's priority vector at full precision (NOT re-derived from the stored matrix, which is rounded to 4 decimals and would move every closeness by ~1e-5), its active criteria (`frozenDroppedCriteria` — a parent that dropped education stays dropped even when an added candidate could be assessed; the disagreement is recorded in `runInfo.rerun.criteriaLiveDisagrees`, not applied), the technical/career anchors and depth targets, and the reference date stint ages are measured to (`recencyFactor` / `stintYears` take `asOf`). Every AHP run now writes what it ranked with to `run_info.frozen`; a child records what it inherited, so a grandchild gets the ROOT's values. A part the parent never recorded is `source: 'live_fallback'`: the service resolves it live, records it in `run_info.frozen`, and fills it into the child's `config_snapshot.rerun.frozen` (the one deferred field of that snapshot).
- **The carried pool is the parent's pool as it was**: not re-filtered for tombstones or for who holds the seat today, because removing anybody is a change the child would misattribute to the people it adds. Carried candidates soft-deleted since are loaded anyway and counted in `runInfo.rerun.carriedDeleted`.
- **The child's snapshot** (`config_snapshot.rerun`, `RunRerunSnapshot`) holds parent/root ids, the reason, `dataPulledAt` (when the new candidates' data was read — separate from the reference date), each added candidate's classification and failed rules, the skipped list, and the frozen basis.
- **The POSITION BASIS is frozen too (FR-RR-07).** Every AHP run records the basis it RESOLVED, as values not ids, in `run_info.frozen.positionBasis`: the target job profile (id, the match tier that found it, a content hash, its responsibilities, competencies and education), the competency reference set and its tier (job profile / critical-position form / incumbent / position aggregate), the education requirement and its source (sealed when it is the incumbent's own — personal data), the career target document vector or synthetic document with its text, the kamus fingerprint, and the embedding model. A child scores its NEW candidates against the parent's basis — same scorers, only the source of their inputs changes, so no formula and no embedding pipeline moved. A parent that predates the basis falls back live PER PART (`live_fallback`, listed in `runInfo.positionBasisStatus.liveParts`), and that is said in the child's banner AND on the comparison page; a kamus / model / dimension move since the parent is a caveat ("Kamus kompetensi berubah sejak run induk"), not a silent change. "Active holder" in the career fallback is judged at the frozen reference date, not today. If HC wants today's job profile, that is a configuration change and therefore a new root.
- **The engine writes the ranking first and `completed` last.** Pool rows and result rows (with the template narrative, `narrativeSource = template`) are written before the LLM narrative, which only updates rows (`narrativeSource = llm`), so a slow writer delays prose, never the ranking (`run_info.timings.rankingReadyAt`). Then `run_info` (with `timings.phasesMs` per phase — measured, never asserted: `scripts/measure-rerun-durations.ts`), then `status = 'completed'`. Readiness labels use the RUN's snapshot thresholds (inherited on a child), never today's (`lib/readiness-label.ts`, FR-SN-04). A failure is recorded on the run as `run_info.failure` (the status check constraint has no `failed`), and every reader shows "Gagal" with the message; the cancel path no longer writes the forbidden `status = 'failed'`.

The table still holds all six modes, because runs carrying the four retired ones exist and must keep their label, chip and `expectation` sentence wherever they render (`rerunSpec()` resolves every stored value; the run tree marks `legacy` ones *mode lama*). scoring-service refuses any session carrying a retired mode or one of the retired keys `ahpAugment` / `ahpExclude` / `ahpAlwaysInclude` (`parseRerunSpec`) — a session queued by the old web app fails with that message instead of being scored under rules that no longer exist.

**Freezing means all six aspects, not three, and their raw inputs.** A child reuses all six of the parent's aspect scores **and the raw strings they were computed from** (`CachedAspects.baseRaw`, persisted as `scoring_run_pool_aspects.details.rawInputs`); without that the detail panel printed this month's PA grade beside a score computed from last month's, and the next derived run read that mismatched pair back. A carried candidate whose parent recorded no raw strings persists `rawInputs: null` rather than today's strings, so a grandchild never mistakes them for the root's. `runInfo.freshness` still measures drift — today's behavior/PA/HAV against the parent's for every carried candidate — and says the drift was deliberately NOT applied; the remedy it names is a new root from the wizard.

**Run lineage is a column, not a jsonb crumb** (`scoring_runs.parent_run_id` + `rerun_mode`, drizzle/0069). The old link lived only inside `runInfo.{augment,exclude}.baseRunId`, which meant it could not be queried in reverse, the full-pool re-run recorded no parent at all (every one of them was a root from its first minute), and it was written by scoring-service at completion so a failed run had no parent. The column is written by the web app at creation. `ON DELETE SET NULL`, never CASCADE — deleting a run must not delete the assessments derived from it; a child whose parent is gone becomes an orphan root and the tree says so. **Parenthood and mode stay separate concepts on purpose**: the legacy `refresh_full` has a parent yet genuinely re-applied the eligibility filters, so it must not inherit the "filters ran on the base run" note. A new child also writes `rerun_reason` (drizzle/0086), shown on its tree node and its detail page. `getRunTreeAction` (`lib/run-tree-actions.ts`) returns the forest **unfiltered by date or program** — the run picker's filters default to the current calendar year, so a January rerun of a December base would render as an orphan and the tree would invent a break that does not exist; filtered-out nodes are dimmed instead. Rendered by `components/analysis/run-tree.tsx` (a "Silsilah" toggle beside the run list) and `components/analysis/run-ancestry.tsx` (a breadcrumb above the ranking, so nobody studies a derived ranking without being told it is one).

**Any two runs of one position compare 1:1** (the "Komparasi Versi" tab of the position page, `?tab=komparasi-versi&a=&b=` — it was "Perbandingan Run" / `perbandingan-run`, which `RESULT_TAB_ALIASES` in lib/run-history.ts still opens; `lib/run-compare.ts:compareRuns`, pure; loaders in `lib/run-compare-data.ts`; actions in `lib/run-compare-actions.ts`). It names the relation (child, descendant, same tree, different root), the five sources a rank can move for — S1 pool composition, S2 weights and active criteria, S3 the six aspect values, S4 the provisional ("skor sementara") flag, S5 filter rules / readiness thresholds / N — grouped as "data or set" (S1, S3, S4) versus "configuration or judgement" (S2, S5), and on a parent → "Tambah Kandidat Pembanding" child anything but S1 differing is shown as a FREEZE VIOLATION (a bug). It then shows the configuration side by side with each item's origin, pool membership with the reason where stored data can tell, ranks and closeness, per-criterion weights/ideals/divisors, a per-candidate TOPSIS breakdown, a fixed-order stepwise attribution (weights → aspects → pool → adjustments; the last step must equal B, tested), deterministic sentences from the catalog in `docs/rerun-explanation-templates.md` (T-01…T-11, no model), and an XLSX export that stores numbers as numbers. The run page's "Selisih Peringkat" panel is the same engine against the parent or root, not a second implementation. **It never recomputes an aspect and never calls a model** (FR-CMP-13); it re-runs TOPSIS from stored aspects with **the scoring-service's own function**: `scoring-service/src/ahp-criteria.ts`, `topsis.ts` (`topsisDetailed`) and `topsis-ranking.ts` (`rankCandidatesByTopsis`) are dependency-free and imported by the web app directly, whitelisted in the web `.dockerignore` — a copy of the formula in `lib/` is forbidden (I-7) and `TC-CMP-STRUCT` fails on one. The same replay backs "Periksa keterulangan" and `scripts/verify-run-reproducibility.ts` (NFR-RR-01). LLM runs are refused with the reason; legacy-mode runs compare like any other. Server-side guard: `comparabilityError` (same tenant, same position, AHP, completed). Every page of it was verified in a browser (`docs/screenshots/rerun/`); status per requirement is in `docs/rerun-requirements-audit.md` §6.

**Comparison and forum decisions are ONE tab of the scoring-results page, "Komparasi Versi"** (`components/analysis/run-compare/run-compare-workspace.tsx`, LAST in `PositionDetailTabs`, directly under "Konfigurasi" — the question it answers, "what changed between these two versions and why", is read after the run's own configuration). It replaced two places that answered one question from two ends: the standalone `/positions/[id]/compare` page — now a server `redirect()` to `compareHref(id, a, b)`, so every old link and bookmark lands on the same pair — and the "Rekomendasi sistem dan keputusan forum" card that sat above every tab (`DecisionSummaryCard` is gone; `components/analysis/decision-summary.tsx` now exports `DecisionRecord`, the tab's "Keputusan forum" section with "Jadikan A/B" per run, and `PairDecisions`, which says in Ringkasan where each chosen successor stands in A and in B). Things that are easy to break:

- **The tab and the pair live in `PositionRunSection`, mirrored into the URL with `history.replaceState`** (`?tab=`, and `a`/`b` while the tab is open; re-applied after a run switch, whose `router.push` drops them). **A run also keeps its calculation TRACE, exported as a live-formula workbook** (drizzle/0092; "Unduh trace perhitungan (XLSX)" beside "Unduh snapshot (JSON)" in the Konfigurasi Run tab → `app/api/scoring-runs/[runId]/trace-xlsx`, audited as `export`). The records above keep most intermediates rounded or not at all — Hungarian cells, per-stint months/recency at full precision, the `T_tahun` IF-chain, the career fallback's holders/union/IDF, PA period weights and D±, TOPSIS norms and ideals — so the scorers fill trace SINKS with values they already compute (nothing changes a number; types in the dependency-free `scoring-service/src/run-trace-types.ts`, whitelisted in the web `.dockerignore`). `scoring_run_traces` holds one `engine` row per run, written BEFORE `completed` (its trigger refuses any write once the run is completed — I-1), and one `pool` row written by `startTournamentSessionAction` (gate, every filter leaf's value and verdict, and the deciding tree as rule-index groups via `traceProgramFilters`); both are sealed under the three-state rule — locked ⇒ not written and `run_info.trace` says why, never plaintext. The DATABASE STATE the anchors were measured from (kamus best-wrong-match, career corpus pairs, topic-family labels, internal moves, appointments, IDF documents) is `scoring_census_snapshots`, keyed by the same fingerprints as the calibrations and insert-if-absent, so a run references a census instead of copying it; a census that cannot be read or stored is not referenced at all. A child copies its carried candidates' entries from the parent's trace, so its own is self-contained. `lib/run-trace/` turns a bundle into a workbook PURELY (`buildTraceWorkbook`): every derived cell is a formula written WITHOUT a cached value, beside the number the run stored, and "Ringkasan" counts mismatches per stage — including against the PERSISTED rows (`scoring_run_pool_aspects`, `analysis_results`), because a trace that agrees with itself but not with the stored ranking must not read "SEMUA COCOK". Traps, each found by recalculating, not by reading:
   - **Criteria are parsed in the READER's locale.** `COUNTIF(r,">0.4")` counts nothing in an Indonesian Excel/LibreOffice (measured: 0 against 2), which turned the mismatch counter into a vacuous all-clear and broke `MAXIFS(…,"<0.999")` in the corpus estimator. Write `">"&cell` or `"<"&0.999`, never a decimal inside a quoted criterion; `v&""` on a number is locale-rendered too, so the pool's `eq`/`in` tests compare a canonical numeric value as a number.
   - **COUNTIF skips error cells**, so the counter adds `SUMPRODUCT(--ISERROR(range))` — an Excel without MAXIFS shows `#NAME?` and must not read as cocok. Functions newer than Excel 2007 need the `_xlfn.` prefix (`fn()` in `lib/run-trace/sheet.ts`).
   - **Runs from before 0092 have no trace** and export degraded: "Panduan" lists what was not recorded, and stored-rounded values are compared at the precision they were stored with (`run_info.ahp` is `toFixed(4)`; prefer `run_info.frozen.ahp.consistency`). A child has no pool row by design — its Pool sheet is built from `config_snapshot.rerun` and cross-checked against the trace's carried set.
   - Verify with `node --conditions=react-server --import tsx scripts/verify-run-trace-export.ts --run <id>`: it recalculates in LibreOffice under en_US AND id_ID, requires zero error cells and SEMUA COCOK, and requires a PLANTED fault to be reported — a counter that cannot see a fault proves nothing.

   Two things about this engine are easy to break by accident:
   - **Every aspect score is 0..100, and the technical aggregate is what enforces it.** A competency pair's cell is `sim′ × levelFactor`, and `levelFactor` reaches `LEVEL_FACTOR_CEILING` (1.75, `TECHNICAL_OVERQUALIFICATION_SURPLUS` + 1) when an *identity* pair sits above the level the JD asked for — while the divisor is the requirement count. So the mean could exceed 1 and this aspect reported **113** on a scale every other aspect, the readiness bands and the AHP weights all treat as 0..100. `matchCompetencySets` now saturates `normalized` at 1 and reports the pre-saturation mean as `normalizedRaw`. The bound lives at the matcher, not the aspect, because the surplus is **compensatory**: over-qualification on one competency may offset a shortfall on another — that is what a mean is for — but it cannot make somebody more than fully qualified, since the criterion asks "can this person do what the JD demands" and that saturates at "yes, all of it". Nothing is hidden; the overshoot still renders per pair and as `normalizedRaw`. This is also the rule the *other* consumer of that number already applied locally — `applyCalibration` (career fallback) truncated the identical surplus at 1 so full coverage stops at the top of its band "and no further" — so technical was the one caller that let it through, and the two disagreed about what full coverage means. Measured before the fix: **6 of 4198 scored rows exceeded 100, all at exactly 113**, in 6 of 179 runs, and capping created **zero** new ties and changed the technical ordering in **zero** runs. Those 6 rows are **not rewritten** — a run is the record of an assessment on a date — so a stored technical above 100 proves the run predates this, and `lib/scoring-explainer.ts`, `components/analysis/aspect-derivations.tsx` and `lib/scoring-methodology-brief.ts` each say so rather than letting it read as the current rule. Rejected alternative: normalising by the *achievable* ceiling `Σ(1 + surplus×(4−r_j)/3)` instead of M. It is the more literal "normalisation" and it is wrong here — it makes the denominator a property of how junior the JD's stated levels are, so the same candidate scores lower against an easier position (a level-1 JD caps at 57 for meeting every requirement, a level-4 JD at 100), and measured on this data it moved **66.7% of rows** and reshuffled the technical ordering in **84 of 154 runs** with nothing to justify the reshuffle.
   - **Embedding-space consistency.** `scoring-service` embeds with the same model and transport as the web app's Job Family rebuild (`lib/job-family/embed.ts`) — Nomic over an OpenAI-compatible endpoint by default — because it compares against vectors *that app wrote* (`job_profile_embed`, `kamus_kompetensi_level_embed`). Changing `EMBEDDING_MODEL` on one side only makes every cosine meaningless without failing anything. The instruction prefix matters too: vectors the web app stored via its OpenAI-compatible path carry no prefix, which `storedVectorKind()` reproduces.
   - **Positions without a job profile.** Technical and career both fall back to the position's *incumbents* (`sync_technical_competencies`, using `proficiency_name`/`score` = the level the JOB demands, not `current_*` = what the holder attained), and career maps that competency coverage onto the run's observed similarity range. Every degradation is recorded in `tournament_sessions.final_ranked.runInfo` and shown on the Progress Running page — when adding a new fallback, surface it there rather than letting a score quietly change meaning. A criterion nobody can be scored on is dropped from the TOPSIS matrix with its AHP weight redistributed, not left as an all-zero column.

When changing scoring logic, keep `lib/scoring-engine.ts` (web, session creation/read/re-run) and scoring-service (`ahp-topsis-engine.ts`, plus the shared loaders left in `scoring-service/src/scoring-engine.ts`: session, position row, readiness bands, HAV quadrant → score) in sync mentally — they share concepts (pool building, grade filtering, readiness levels) but are separate files in separate deployables and can drift.

**MCU is not a disqualifier and not a criterion — it only flags.** `mcuStatus in ('fit','fit_with_note')` used to be a hard filter in all three system programs, so an `unfit` candidate was never scored at all: no rank, no explanation, just a one-line rejection. A medical finding does not make somebody less competent for a seat, so the rule is now ADVISORY: it flags and never disqualifies, and nothing MCU-related reaches a score, a rank or a criterion.

Adding a seventh AHP key was the obvious alternative and is the one to keep refusing: `AHP_CRITERIA_ORDER` is the row/column order of every **stored** pairwise matrix, so growing it to 7 makes each stored 6×6 fail `isValidPairwise` and fall *silently* back to `DEFAULT_WEIGHTS` — including the matrix a derived run pins from its base run precisely so the weights cannot move. The data would not have supported a criterion anyway: MCU has three values, and TOPSIS contributes exactly nothing from a column where everyone is identical.

'severity'`), not per row, because a template can hold another rule that already has a severity and a row-level guard would skip MCU forever. `config_snapshot` is deliberately untouched: those runs really were judged with MCU as a knockout.

Stripping can empty a group, and an empty group — `and` or `or` alike — must stay vacuously satisfied, or a program whose MCU rule sat alone in one would disqualify everybody. **AHP is the ONLY weighting surface** (drizzle/0074). The share each aspect carries comes from the program's pairwise matrix, or from the system defaults when a program has none; `scoring-service/src/ahp-weights.ts` owns that resolution. A program's criteria list (`default_criteria`) carries no weight and **no engine reads it** — AHP + TOPSIS scores all six aspects; the list is descriptive and is frozen into each run's `config_snapshot`. Before 0074 the (since deleted) AI Tournament took its weights from that list's own numbers while AHP took them from the matrix — one program, two weighting editors that disagreed in this database (Emergency: PA 10 / education 5 in Mulia, PA 20 / education 0 in ERRO and MSO). `DefaultCriterion.weight` survives as optional and `@deprecated` only because `RunConfigSnapshot` holds frozen copies of runs that really were weighted that way. `lib/scoring-criteria.ts` keeps the canonical criterion names (`CANONICAL_CRITERIA`, `matchCanonicalCriterion`) for the program pages that still list them.

**The AHP matrix is a canonical Saaty matrix, and every input mode is a projection of it** (docs/ahp-input-sync.md). The governance editor (`components/governance/governance-ahp-editor.tsx`) has four views — Urutan, Slider, and Berpasangan as Daftar or Matriks — and `value.pairwise` is the only data: slider positions, the order, both pairwise views and the CR badge are derived from it on every render, so switching modes never writes and never rounds. Every WRITE goes through `lib/ahp-input.ts` and leaves all 30 off-diagonal cells on S = {1/9…1/2, 1, 2…9} (lower triangle = the table reciprocal, so 1/3's twin is exactly 3): Slider (weight in %, 2–65, commit on release) rewrites only the moved criterion's 5 judgments and advances past a dead zone instead of snapping back to where it was; Urutan permutes the existing weight values onto the dragged order and rewrites all 15 (snap is monotone, so it can tie but never invert — pinned over 720 orderings); "Atur Bobot AHP" seeds the system defaults snapped (26.09/4.97/34.37/9.43/20.17/4.97 %, CR 0.0054 — deliberately not exactly 35/25/20/10/5/5). This replaced `snapInteger`, a DISPLAY-only `Math.round` that showed a stored 1.25 as 1 while the server validated 1.25: an expert saw CR 0.1118 and the system accepted CR 0.0995 (run 622af32e), and the lower triangle printed "1/2" over a stored 2. Cells commit on blur/Enter from their own draft — never from onChange, which React does not fire for a retyped identical digit. **One implementation decides validity:** `validateAhpPairwise` in `scoring-service/src/ahp-saaty.ts` (log-space scale check, reciprocal, diagonal, CR ≤ 0.1), imported directly by the web app (whitelisted in `.dockerignore`), and `lib/ahp.ts` now RE-EXPORTS `computeAhpWeights` & co. from `scoring-service/src/ahp.ts` instead of keeping a duplicate — so the editor badge, `saveAhpConfigAction`, `updateProgramTemplateAction`, the new-session gate, the engine flag, the run configuration panel and the audit script cannot disagree. `isValidPairwise` stays STRUCTURAL on purpose: it is the engine's usability gate, and tightening it would silently fall back to default weights for older data. The program-level save leaves a matrix untouched only when it equals the value stored in `program_templates.ahp_config` (decided server-side in `lib/ahp-save-rules.ts`, never by a client flag), so a program holding an older off-scale matrix can still be renamed; a NEW scoring session (wizard, bulk auto-score, program re-score) is refused while the stored matrix fails validation. The engine's scoring path is unchanged — it only records `run_info.ahp.inputCheck` / `trace.ahp.inputCheck` (system defaults are off-scale by construction and marked `expected`), and `run_info.ahp.pairwise` is now full precision with `pairwiseLabels` and `pairwisePrecision: 'full'`; readers check older runs at display time (1e-3 in log space for their 4-decimal copy). `scripts/audit-ahp-saaty.ts` lists stored configurations and run snapshots that are off-scale or non-reciprocal, inside `BEGIN READ ONLY`. Tests: `pnpm test:governance`, `pnpm test:governance:browser` (real editor in Chromium), `npx tsx scripts/verify-ahp-modes.ts`, and the stack E2E `tests/governance/ahp-e2e.stack.ts` (local DB only — it writes).

**Both similarity scales are derived from their corpus, not hardcoded** — and they are two separate calibrations over two separate corpora, so keep them apart: technical measures `kamus_kompetensi_level_embed`, career measures `job_profile_embed`.

**The career similarity anchors are measured by THREE independent estimators whose MEDIAN wins** (`scoring-service/src/career-anchors.ts`, cached in `job_profile_similarity_calibration`, drizzle/0066 + drizzle/0068). Two rounds got them here, and the second is the one worth understanding.

Round 1 (drizzle/0066) stopped them being hardcoded per model family, measuring `simFloor`/`simCeil` as **p25 of arbitrary cross-document pairs** / **p99 of each document's nearest genuine twin after pairs ≥ 0.999 are dropped** — 0.519 / 0.998 on this corpus. Measuring beat guessing, but that floor answers a question nobody can check, and calibrating against observable labels shows where it lands: **at cosine 0.519 the probability two profiles are even in the same job family is 10%.** So `sim'` = 0 sat where 90% of pairs are unrelated and everything above earned positive relevance — career multiplies `sim'` by years and *accumulates*, so a 12-year unrelated career banked ~4.7 effective relevant years against a target of ~7.

Round 2 (drizzle/0068) therefore asks the same question three ways and takes the median, so no single estimator can move the scale alone, an unavailable one degrades gracefully, and a wrong one is outvoted:

| estimator | measures | measured here |
|---|---|---|
| `corpus` | the round-1 method. Needs no labels, so it is always available and is why this never returns nothing. | 0.519 – 0.998 |
| `family` | the cosine at which running precision against `job_family_topic_assignments` (last **completed** run) falls through 50% / 95%. Partly circular — those families were clustered from these vectors. | 0.672 – 0.878 |
| `transitions` | **revealed preference**: p10 / p75 of the cosines of internal moves people *actually made*, from `candidate_position_history` in `valid_from` order. The only non-circular estimator; restricted to the filename-code and exact-title tiers, because pairing a stint *by cosine* and then measuring that cosine would be circular where circularity is not already acknowledged. | 0.633 – 0.892 (102 moves) |
| **resolved** | median | **0.633 – 0.892** |

The transitions estimator is also the independent check on the whole thing: real internal moves have median cosine **0.827** against 0.562 for arbitrary pairs, and the old floor of 0.519 sat **below the 10th percentile** of moves that really happened.

**The fingerprint has to cover every input the estimators read, and that took two corrections.** It is `md5(job_profile_id, content_hash …) : model : t<topicRun>/<n>/h<historyHash> : METHOD_VERSION`. `METHOD_VERSION` came first: when the estimator set changed the corpus had NOT moved, so the fingerprint matched and every deployment kept serving the single-estimator numbers — a wrong answer with a 200 response and a completed run. Bump it whenever what the estimators compute changes. The **label components** came second, for the same reason one level out: `family` reads a topic run and `transitions` reads `candidate_position_history`, and both move without the vectors moving — a re-clustering reassigns every topic id (8 completed topic runs exist here) and the Monday sync adds stints. An earlier comment argued those estimators were "stable in aggregate"; that is wrong in the way that matters, since the failure is invisible and the fix is one aggregate query. History is *hashed* over the ordered `(candidate, position, valid_from)` set rather than counted, because a corrected date reorders a career and changes which pairs are moves. `measureFamily` and the fingerprint select the topic run by the **same** rule — newest completed run *that has assignments*, since "completed" is not proof of content — because naming one run and reading another would make the cache stale forever. The composite is clamped to the column width: `store()` swallows write errors, so an overflow would fail silently and re-census every run, which is the drizzle/0067 trap. **One change no fingerprint can see** is a re-embed producing different vectors from identical text and model, which is precisely why `rebuildJobProfileEmbeddings` re-embeds unconditionally — so it calls the refresh with `?force=1`. `CAREER_SIM_FLOOR`+`CAREER_SIM_CEIL` still pin the pair; the old constants (0.45/0.85 non-E5) survive only for a corpus that is missing, under 30 documents, or degenerate. `POST /api/embed/career-anchors/refresh` makes a recompute immediate after a job-profile rebuild.

**The competency fallback is now a CAPPED, IDF-weighted band, not the run's own percentiles.** A stint with no job profile is scored from the incumbents' competencies, and that 0..1 coverage used to be mapped onto `p5..p95` of the document similarities *in that run*. The stated intent was that a fallback "must not out-score a real document match"; the implementation inverted it, because p95 of a few dozen stints is very nearly their maximum — on the IT Application Development Department Head run the band came out `[0.563, 0.949]`, and 0.949 is exactly that target's cosine against its own *IT Application Development Analyst* JD. Full competency coverage bought the claim "this IS the job". Measured over 660 scored candidates in 8 runs: **document-scored candidates averaged 35.1, fallback-scored ones 66.7**, and 90 of the 104 scoring ≥ 90 had fallback evidence — the criterion was reporting how much of a history *lacked* a job profile. Now: `[simFloor, simFloor + cap × (simCeil − simFloor)]` with `CAREER_FALLBACK_CAP` = 0.5 (measured: the fallback separates job families at AUC 0.743 against the cosine's 0.874, and 5% of unrelated job pairs share ≥ 75% of their competencies), and coverage is **IDF-weighted** (`scoring-service/src/competency-idf.ts`) because the vocabulary is dominated by near-universal entries — `SOFTWARE APPLICATION OPERATION` on 92.7% of 275 JDs — so an unrelated manager covered ~45% of any position's requirements for being a manager at all. Weighting by `ln(N/df)` drops the median coverage of an unrelated pair from 0.286 to 0.104. **The technical aspect deliberately does not use IDF** and its numbers are unchanged to the bit: there the question is "can this person do what the JD demands", where a common requirement being common does not excuse missing it — so `matchCompetencySets` takes the weights as an optional argument and only career passes them.

**The career depth yardstick `T` is now ABSOLUTE, and that was the user-visible bug.** It used to be median-of-pool × 2, which made career the only pool-relative quantity among the six aspects — and gave it a fatal corollary: the yardstick shrinks exactly when the bench is weakest. Measured on runs in the database now, a Learning & Development pool whose average relevance was 0.168 produced `T` = 2.06 years / **1.0** stints (the second pinned at its clamp floor, so ONE stint saturated that axis) and averaged 33.1; against a fixed 8/2 the same people score 11.3. The inflation ran 1.4× on a normal pool and 3× on a bad one, always toward making a weak bench look viable. Now: `inherited` on an incremental run → `jd`, the target profile's own `jobSpecification.experience` **as written** (`CAREER_DEPTH_STATED_MULTIPLIER`, default **1**) → `fixed` 8 years / 2 stints. The multiplier was 2, on the argument that a stated requirement is a *minimum to be eligible* rather than the point deserving 100; it is 1 because doubling was the code overruling the JD — a seat asking for 3 years had its bar silently set at 6 — and because the feared corollary did not materialise: measured on 1,784 candidate×position pairs, dropping to ×1 takes the average career score 37.9 → 62.1 but leaves only **11%** at 100 (not "everyone who qualifies"), since `effectiveYears` is relevance-weighted and age-decayed, so clearing 3 years of *tenure* is not 3 *effective relevant* years. **The multiplier used to double as the gate** — the JD was read only when `stated × mult > fixedTargetYears` — which made "stop doubling" mean "ignore the JD": of 179 profiles with a parseable requirement, 2 exceed 8 years, so 177 seats would have used the house default while `source` claimed `jd`. The gate is now its own flag (`CAREER_DEPTH_STATED_ONLY_ABOVE_FIXED`, default off), and `min/maxTargetYears` 3–20 still clamp — which at ×1 actually bites, since 59 profiles state 1 year and 38 state 2, all landing on 3. Each run records its own `statedExperienceMultiplier`, and every reader defaults a missing one to 2 rather than to today's setting. `pool` can only appear on runs finished before this change and is still labelled as pool-relative everywhere it renders. The pool medians are still measured and reported as diagnostics.

   **All of the above describes what `deriveDepthTargets` was supposed to do; until now it did not compile, and the half that ran was the old rule.** The function carried a duplicate `const targetRows` and a return missing seven fields of `CareerDepthTargets` — three TypeScript errors that `next.config.mjs`'s `ignoreBuildErrors` let ship — while `statedMode`, `statedExperienceOnlyAboveFixed` and `defaultSource` sat in `config.ts` unread. It now implements them, which changes scores in two ways worth expecting. **(1) A fourth source, `measured`, sits between `jd` and `fixed`** (`CAREER_DEPTH_DEFAULT_SOURCE`, default `measured`): when the JD states nothing parseable, `T` is the median years of service the people *actually appointed* to a seat at that seniority band had behind them, from `candidate_position_history` via `career-depth-anchors.ts` — the same revealed-preference evidence the `transitions` similarity anchor uses. Measured here over 470 appointments: staff 5.7, officer 7.0, section head 8.0, department head 9.25, division head 15.5, with a monotonicity guard so a thin senior band can never end up easier than a junior one. **(2) `statedExperienceOnlyAboveFixed` being off now actually means it** — a JD stating 3 years sets the bar at 3 (clamped to `minTargetYears`) instead of being silently discarded in favour of the house default. Measured over the 275 profiles here: 174 state a parseable requirement, and under the broken gate exactly **2** of them (the ones stating 10 years) ever reached `source: jd` — the other 172 silently used the house 8. Now 147 land on T = 3, 23 on 5, 2 on 4, 2 on 10. So this **raises career scores on most seats** (bar 8 → 3) and **lowers them on senior seats with no parseable requirement** (8 → the level median, 9.25 for a Department Head, 15.5 for a Division Head). Set `CAREER_DEPTH_STATED_ONLY_ABOVE_FIXED=1` to restore the old "a JD may only raise the bar" behaviour, or `CAREER_DEPTH_DEFAULT_SOURCE=constant` to keep the flat 8 when no JD states anything. `statedIgnoredReason` distinguishes `mode-ignore` from `below-floor`, because "the JD says nothing" and "the JD says 1 year and something else won" are different findings.

Two more shape changes, both measured rather than reasoned: **depth carries the score and breadth only modulates it** (`depthYears × (1 − w + w × depthRows)`, `w` = 0.25) — this replaced `min(depthYears, depthRows)`, whose "one long stint is capped by the rows axis" rationale threw away the strongest evidence the criterion can receive: a candidate with 10.6 years as an IT Application Development Analyst scored **47** while support-only candidates scored **100**. And **relevance decays with age** at `exp(−0.043 × years since the stint ended)`, the skill-depreciation rate from the human-capital literature; nothing decayed before, so a stint ending in 2006 counted as much as the one the candidate holds today and `CareerPair.isCurrent` never reached the score. The **Mincer concave form is implemented but default-off** (`CAREER_DEPTH_CONCAVITY` = 1): human-capital theory says returns to experience are concave, and measured here it made this objective *worse*, because diminishing returns lift the middle of the scale and the middle is where long-but-irrelevant careers sit (separation +39 at γ=1 → +24 at γ=2). Right for modelling what experience earns, wrong for deciding whether experience is relevant.

Net effect on the reference run: the two genuine app-dev candidates now rank 1st and 2nd (100, 90) where one of them had been *below* four support-only candidates tied at 100; those four now score 35–51. Separation between genuine and spurious relevance went from **−15 to +39**. Rank correlation with the old ordering is 0.87–0.90, so this is not a reshuffle — it is the specific inversions being corrected.

Re-baselining is a **deliberate score shift, not a silent bugfix** — runs keep their own `runInfo.career.scale` (now including the estimator breakdown), `.depth`, and `.calibration`, so a ranking finished under the old rules stays explainable and *visibly* incomparable. Every reader labels the retired sources (`pool`, `empirical`) as legacy rather than rendering them as if they were current: `components/analysis/run-configuration-panel.tsx`, `components/analysis/aspect-derivations.tsx`, `lib/scoring-explainer.ts`, and `lib/scoring-methodology-brief.ts` (which also instructs the assistant to say so out loud when asked about such a run).

A trap both calibrations shared: `fingerprint` is `md5(corpus):embedding_model`, up to 153 characters, and drizzle/0064 sized it `varchar(64)`. `store()` wraps its INSERT in a catch on purpose — an unapplied migration must not fail a scoring run — so a *permanent* write failure looked exactly like a transient one, and the kamus census re-ran on every single tournament instead of once per corpus change. drizzle/0067 widens both to 200. When adding a calibration, check the fingerprint column can hold the model name.

**The technical similarity anchors are derived from the kamus corpus, not hardcoded.** `simFloor`/`simCeil` (what a semantic competency cosine is stretched onto 0..1 with) describe one embedding corpus, so a re-embed, an added/removed competency, or a model switch silently changes what a technical score means while every cosine keeps computing. They live in `kamus_similarity_calibration` (drizzle/0064) keyed by a fingerprint over every embedded row's `(code, level, content_hash)` plus the model, so `scoring-service/src/technical-anchors.ts` recomputes on ANY change without each write path knowing — a run self-heals, and `POST /api/embed/technical-anchors/refresh` (called when a kamus re-embed finishes) just makes it immediate. floor = p25 and ceil = **p99** of the per-row best-wrong-match distribution; p99 rather than the max because one near-duplicate competency would otherwise drag the ceiling to ~0.99 and compress the scale. `TECHNICAL_SIM_FLOOR`+`TECHNICAL_SIM_CEIL` still pin it. This is not the per-run percentile approach career's *scale* refuses — those track the pool, these track the instrument, and every run records its own anchors in `runInfo.technical`. (Career now measures its own scale the same way, from three estimators rather than one — and **no per-run percentile survives on that side at all**: its fallback calibration used to be the run's own p5/p95 and is now an absolute capped band, for the reasons above.) The **"Konfigurasi Run" sub-tab states all of this on the page** (`components/analysis/run-configuration-panel.tsx`): the values, a badge saying whether they were measured / pinned / a fallback, the census they came from, and why per-run percentiles are refused while a kamus change forces a recompute — because both misreadings ("they are constants" and "they changed, so runs are incomparable") are wrong in opposite directions and neither is answerable from the numbers alone.

**Weights have exactly two tiers: the program's own `ahp_config` matrix, else the system defaults.** The defaults are one constant — `DEFAULT_ASPECT_WEIGHTS` in `lib/scoring-criteria.ts`: behavior 35, technical 25, HAV 20, PA 10, career 5, education 5 — mirrored as `DEFAULT_WEIGHTS` in `scoring-service/src/ahp-weights.ts` and used as the governance pairwise editor's starting point (`activate()` derives 1–10 slider points from it, so the matrix it writes reproduces those weights exactly at CR = 0). Most programs have no matrix, so in practice the defaults ARE the configuration, and two runs of different programs are comparable by construction. `ahpWeightPercentages()` (`lib/scoring-criteria.ts`) is the web app's copy of those two tiers — anything reporting "the weights in force" should call it rather than assume equal shares or read a criteria list.

A third tier used to sit in the middle — deriving the matrix from the program's "Kriteria & Bobot" list — and its removal (drizzle/0061) was the first half of making AHP the only weighting; drizzle/0074 is the second, taking the weights off that list entirely. A criterion at weight 0 even used to fall back to its default under the old derived tier instead of counting as 0. Runs finished under the old rule keep `criteria-weights` in their own stored `runInfo`; `components/analysis/run-configuration-panel.tsx` still labels that value, marked *(aturan lama)*, and only then prints the criteria table with the weights that run really used.

#### Optimization panel

Pengaturan Job Family (`/posisi/job-family/pengaturan`) carries a **button panel**, not a chat
(`components/job-family/optimizer-panel.tsx`). One button per entry in
`OPTIMIZE_GOALS` (`lib/job-family/optimize/objective.ts`), plus inspect / outlier-detail.
It uses **no LLM at all**, and that is the point: the set of things a
user can want from a clustering is finite and already enumerated, so a text box
would only insert a guess — user phrases a sentence, a model guesses which goal it
meant — in front of an answer that was already determined. It briefly was a chat,
and the two failures that produced were both guessing failures: a run id
transcribed by hand with a character dropped, and a needless clarification turn.

**A goal button MEASURES; it does not predict.** It used to propose a setting
computed from the last completed map — which after a re-embed describes a corpus
that no longer exists — and offered to apply it unmeasured. Now
`startOptimizationSearchAction` / `stepOptimizationSearchAction`
(`lib/job-family-optimize-actions.ts`) drive a search whose planner is pure
(`lib/job-family/optimize/search.ts`): round 0 measures the setting in force on the
corpus embedded NOW, round 1 the `candidatesFor` directions from that measurement,
later rounds continue from the candidate closest to the goal and try a milder
version of any that met it at a price (≤ 3 rounds, ≤ 16 trials, all inside
`space.ts`'s BOUNDS). The measurement is topic-service's `POST /topics/trials`,
which runs `pipeline.cluster()` — the very function a build runs — and persists
nothing (a trial run would become "the latest completed run" that the map,
scoring's career anchors and diagnosis read). Each goal is judged by ONE stated
number (`goalVerdict` in `lib/job-family/optimize/measured.ts`, the same text as the
button's hint); what else got worse is reported separately (`sideEffects`, minus
the metric the goal moves by definition). Only a candidate measured to MEET the
goal is offered; when none does, the card says "Tidak tercapai dalam rentang aman"
and offers nothing. This is the strongest honest guarantee available — some goals
are unreachable on some corpora, and clustering is not monotone in its knobs — so
never reword "not met" as a partial success. `cleaner_labels` is judged by a PROXY
(shared top keywords across families, with membership required unchanged) and says so.

Things that are easy to break:

- **The browser holds only trial ids.** Every step re-reads the batches from
  topic-service and re-runs the deterministic planner, and
  `applyMeasuredOptimizationAction` re-derives the verdict the same way, so the
  browser can never hand the server a measurement topic-service did not make, and a
  web restart loses nothing. Poll steps strictly one after another: a step may start
  the next round, and a concurrent second step would try to start it again.
- **Apply is refused unless it is still the measured situation**: the corpus
  fingerprint now must equal the measured one, and `saveBertopicConfigAction`'s
  `expectBertopic` re-checks the parameters in force UNDER the config write lock.
- **The corpus fingerprint has one formula in two places**: topic-service
  `db.corpus_fingerprint` and web `lib/job-family/corpus.ts` — md5 over
  `job_profile_id:md5(document):md5(vector text)` in id order, the per-row hashes
  computed by Postgres on both sides. Runs record theirs in `diagnostics.corpus`;
  `getMapFreshnessAction` compares it with the corpus now (pre-fingerprint runs are
  judged from count + last embed time and say so). It hashes vectors, not
  `content_hash`, because a re-embed can change vectors for identical text.
- **Verification after a rebuild** (`getOptimizationVerificationAction`) finds the
  measurement by sha256 of `configKey(bertopic)` in
  `job_family_optimization_expectations` (drizzle/0090), not by config version, so
  a template save in between does not lose it, and it works for "Simpan saja, bangun
  nanti" plus a rebuild days later from the map page. Same corpus ⇒ the map must
  equal the measurement (sizes and outliers), and a mismatch is shown, not smoothed
  over. Sizes are read from `job_family_topics`, because manual outlier mapping
  rewrites assignments.
- **Builds outrank trials in topic-service**: one compute lock; a build arriving
  mid-batch is accepted and the batch stops after its current config.

The reasoning is deterministic code. Four registry tools (`job_family.read_config` /
`.diagnose_clustering` / `.explain_outliers` / `.apply_config`) once wrapped it inside
Agent Studio, which is **deleted from main**, so they went with branch
`parked/agent-studio`; see [`docs/agent-studio-parked.md`](docs/agent-studio-parked.md).
The implementation moved from `lib/agent/optimize/` to `lib/job-family/optimize/`

Three invariants worth keeping:

  Not an inconsistency: parameters are global, so judging them from one unit's

- **Readers resolve the last COMPLETED run**, via
  `getLatestCompletedTopicRunAction`. Using the newest row of any status lets one
  failed run close diagnosis permanently while good results sit right behind it —
  and it disagrees with the `topic_run_available` precondition, which already
  filters on `completed`.
- **Applying is global and must say so.** Every config save (`saveConfigPart`)
  deactivates every `is_active` row regardless of tenant; the panel prints that

**Each settings control saves ONE part of the config, and the server does the merge** (`lib/job-family-actions.ts`). `saveRestructureTemplateAction`, `saveRestructureOverrideAction` (one profile), `saveBertopicConfigAction` (also the optimizer's apply) and `saveEmbeddingConfigAction` (Settings → Sinkronisasi) all go through `saveConfigPart`: read the active version under an advisory lock, replace their part, insert the result as the new active version. The old `updateJobFamilyConfigAction` took the whole object from the browser, so every save also wrote every other part as that tab held it: an unsaved template went live with a parameter save, a page loaded before somebody else's save reverted it, and a stale Sinkronisasi tab could put an old template back right before re-embedding the corpus. On the client, `rebaseConfigDraft` carries the draft onto each saved config without discarding another part's unsaved edits, and a Simpan button is disabled while its part is clean. `normalizeJobFamilyConfig` reads a stored config in today's exact shape; stored rows still carry the retired `bertopic.minTopicSize` / `language`, and kept, they made the strict per-part save refuse every parameter save on an existing install. The visual template editor's rules (sections, headings, free text, a profile edit never touching the global template) live in `lib/job-family/template-editor.ts` and `editProfileTemplate`, pinned by `pnpm test:job-family`.

**A map build keeps its calculation TRACE, exported as a live-formula workbook** (drizzle/0094; "Unduh trace perhitungan (XLSX)" beside "Kembali ke Peta Job Family" on `/job-profiles/job-family/pengaturan` → `app/api/job-family/trace-xlsx`, gated by `job_profiles.view`, readable only where the map is, audited as `export` on `job_family_topic_runs`). topic-service copies every intermediate out of the fitted models into `job_family_topic_traces` (one gzip-JSON row per run, `topic-service/app/trace.py`; its README § "Calculation trace" lists what and the three places the library hides it), and the web app now stores the provenance a document's text needs — `job_profile_embed.embed_template / embed_source / embed_dimensions / extracted_hash`, written by all three embed paths. `lib/job-family-trace/` turns a bundle into a workbook PURELY (`buildJobFamilyTraceWorkbook`), same conventions as the scoring trace (no cached values, `_xlfn.`, P_ names, a live mismatch counter in Ringkasan): Parameter (the corpus clamps as formulas) → Kondisi Database (fingerprint, models, statuses then vs now) → Dokumen / Dokumen - Baris (extracted data + template → the embedded text, line by line) → Vektor / Jarak Cosine → UMAP (kNN, the σ bisection written out, fuzzy union, pruning, the a/b least-squares gradient) → HDBSCAN (Euclid, core, MST, union-find, single linkage and its condensation, stability, EOM with the library's `cdef float` rounding, labels, soft membership) → BERTopic topic ids, re-homing, c-TF-IDF, keywords and labels, reasons, 2-D positions, representatives, Family Tree (Lance–Williams Ward), generalization, seed ARI → Hasil Akhir against the persisted rows. What stays an INPUT, each proved where a formula can prove it: the kNN choice (SMALL = k smallest), the MST edge list (approximate Borůvka), UMAP's SGD coordinates, tokenizer counts and keyword presence, the BFS order condensation walks (a check column proves it breadth-first), alternative-seed partitions, `nrTopics` merges, model-written titles. Traps, each found by recalculating, not by reading:
   - **A recursive column must never reference a range containing itself.** LibreOffice evaluates INDEX lazily and lets it pass; Excel's static dependency graph calls it circular; a COUNTIFS over such a column is circular in both (measured: 7,489 error cells). Tree recursion therefore reads only the rows ABOVE (selection, ancestors: parents have smaller ids) or BELOW (single linkage: parents merge later), and the BFS rank is a recorded traversal plus a validity check instead of a COUNTIFS rank.
   - **A reference to an empty cell is 0, not ""** — the document rebuild turned every blank line into "0" until the reference was coerced with `&""`.
   - **`-x^p` is `(-x)^p`** in Excel and LibreOffice (#NUM! for a fractional p): write `-(x^p)`.
   - **Python `round` and Excel `ROUND` disagree on decimal ties** (0,68285 → 0,6828 vs 0,6829): a value the run stored rounded is compared UNROUNDED within half a unit of its last decimal.
   - **Ties belong to the library**: topic numbering is a quicksort over sizes and keyword order an argpartition, so those checks compare the k-th SIZE/WEIGHT (LARGE), never identity. A document rebuild may legitimately differ when the embed template was not recorded (vectors from before 0094) or the extracted data changed since — only a recorded template with unchanged data counts as BEDA.
   Size at production scale (275 documents, 39 families): ~0.9 M cells, ~20 MB, ~18 s LibreOffice recalculation — which is why there is no unit-vector sheet (cosine is written from the raw vectors and their norms) and the σ sheet stops at the slowest document's iteration count plus a margin (a "Konvergen" column proves nothing was cut). Verify with `node --conditions=react-server --import tsx scripts/verify-job-family-trace-export.ts [--run <id>]`: both locales, zero error cells, SEMUA COCOK, and two PLANTED faults (a persisted similarity, a recorded HDBSCAN label) each caught by the check that owns its stage. Demo mode masks the job-profile file names (position codes, JD numbers); nothing else in the workbook is an identifier.

### Database

Single Postgres database, schema owned by the web app at `lib/db/schema.ts` (Drizzle ORM), migrations in `drizzle/`. Both other services connect to the same DB with their own lightweight clients (`sync-service/src/db/postgres.ts`, `scoring-service/src/db/postgres.ts`) — schema changes made via Drizzle in the web app affect all three, so check for row shapes used by `sync-service`/`scoring-service` before renaming/dropping columns. `DATABASE_URL` and `POSTGRES_URL` are used interchangeably across services — the web app checks both (`lib/db/index.ts`).

Key tables: `tenants`, `users`, `positions` (synced master positions), `critical_positions` (tenant-curated successor-relevant roles, with grade range/required competencies, one per succession program), `candidates` (+ `candidate_technical_competencies`, `candidate_position_history`), `program_templates`, `tournament_sessions`, `scoring_runs`, `analysis_results`, plus sync-owned tables (`employees`, `performance_appraisals`, `disciplinary_records`, `sync_employee_personal`, `sync_job_profiles` + its ownership table `job_profile_tenants`, etc.).

**Candidate age is derived, never stored.** `sync_employee_personal` (job `personal`, `POST /sync/personal`) pages through `/employeeV1/employee/Information` — a *listing* endpoint, unlike the per-employee disciplinary/education ones — and keeps only the birth date and display name out of a payload that also carries national ID, NPWP, BPJS, phone and email; nothing here would read those, and they would only widen what a database leak costs. `candidate-populate` copies the birth date onto `candidates.birth_date` (encrypted like every other candidate field), and `candidateAge()` in `lib/age.ts` turns it into a number at render time. Both upserts keep an existing birth date when the source returns none (`COALESCE(EXCLUDED…, existing)`), because this job runs unattended on the Monday cron and one blank upstream response must not erase everyone's age.

**Competency names resolve to a kamus CODE before they are matched** (`lib/kamus-name-match.ts`, cache `kamus_competency_match_cache`, drizzle/0063). Identity is the code, not the string, because required names come from LLM-extracted job-profile PDFs and drift from the dictionary — a profile says `Business Process Analyst` where the kamus and HR sync say `BUSINESS PROCESS ANALYSIS` (34 of 102 distinct required names match no kamus entry; 2 of 65 on the candidate side). The cost of a miss is a *wrong pairing*, not a missing vector: an unresolved column has no level vector so every cell is 0, and since Hungarian maximises, the candidate competency that belonged there gets spent elsewhere. Three tiers — exact, a deterministic token match accepted only when unique, then an LLM restricted to SPELLING equivalence over the whole 90-entry kamus (same keywords, differing only by typo/inflection/word order; adding, dropping or substituting a meaningful word must be "none", confidence floor 0.9). **The resolver lives in the web app and scoring-service only reads the cache**, because scoring must stay runnable with no model reachable (the orphan sweeper restarts sessions unattended); the web app primes inside `notifyScoringService`, capped by `KAMUS_AI_MAX_NAMES_PER_RUN`, with an uncapped "Petakan" button on `/settings/sync`. A required competency that resolves to nothing AND that no candidate holds by name is **dropped from the divisor** rather than counted as a zero everyone shares, and reported as `matchType: "unmeasurable"`. See `scoring-service/README.md` § "Competency identity is the kamus CODE".

**Job-profile matching has four automatic tiers plus a manual pin** (`lib/job-family-sync-actions.ts: getJobFamilyMatchReport`): position code in the JD file name → identical title → embedding cosine > 0.98 → **AI**. The AI tier (`lib/job-family/ai-match.ts`) exists because the three deterministic ones are exact by construction and the leftovers are the long tail they cannot express — abbreviations (`SPV ADM GUDANG`), reordered words, titles written from the org chart rather than the JD. It calls the app's own OpenAI-compatible endpoint (`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`, the same local model the rest of the app uses — not Gemini) at temperature 0.

Three properties keep it from becoming a guess generator, and all three are load-bearing:

- **It may only pick from a shortlist** of the ~10 nearest profiles by embedding, and an id outside that list is rejected on parse — the model arbitrates, it never searches or invents.
- **"None" is a first-class answer**, and anything under `AI_MATCH_MIN_CONFIDENCE` is discarded. A wrong JD is worse than no JD: it silently changes a candidate's technical and career aspect scores during AHP+TOPSIS, where nobody would look for the cause.
- **Decisions are cached per normalized title** (`job_family_ai_match_cache`, drizzle/0059) — including rejections. An LLM is not a pure function, so without the cache the same title could pair differently between two page loads and the report would reshuffle under the operator; the cache also means a title costs one call ever, not one per report load. `AI_MATCH_MAX_TITLES_PER_RUN` caps a cold start, and the surplus is reported as `aiDeferredTitles` rather than silently dropped.

An unreachable model reports `aiAvailable: false` (a banner) instead of an empty answer — an outage must never read as "AI found nothing" and unmatch people. Manual pins still outrank every tier including this one.

**A job profile's FILE NAME is a second title, and matching now uses both.** The title extracted from inside the PDF and the title in its file name routinely disagree — 64 of 256 parsed names on this corpus — and the file name is frequently the one naming the seat the document is actually FOR. Three files here share one extracted `position_name` ("System Integrator Analyst") while their names say System Integrator Analyst, System Integrator Junior Analyst and Main Dealer Management System Business Analyst, so two of those three seats could never match on content alone. `buildDeterministicMatcher` (`lib/job-family/match.ts`) therefore keeps a second index over `parseJobProfileFileName(...).title` and reports those as `matchType: 'file-alias'` ("Nama Berkas" in the report). Measured: the deterministic tier goes **189 → 216** of 1,163 distinct `sync_positions` titles, +27, including `MAIN DEALER MANAGEMENT SYSTEM BUSINESS ANALYST` → the file whose PDF says "System Integrator Analyst". Always on, no toggle.

Three things hold it together. **An alias claimed by more than one profile is dropped entirely** (15 here — "cashier", "legal deputy department head"): a wrong JD is worse than no JD, because it silently moves technical and career aspect scores during AHP+TOPSIS where nobody would look for the cause, so an ambiguous name must fall through to the embedding/AI tiers that can weigh context instead of guessing. **The alias index is consulted only after the exact one**, so nothing that matches today changes its answer. And `parseJobProfileFileName` had to learn two things before the aliases were usable at all: strip a trailing `(Rev. 2)` (document versioning, not part of a job title) and handle the one file written `JD -MSD-022` with a space, which otherwise glued `-MSD-022` to the front of the title.

**`ProfileLite.fileName` is REQUIRED on purpose.** As an optional field it produced a whole matching tier that looked wired up, type-checked, and matched nothing — the two places that build `ProfileLite` list every field by hand and neither supplied it. Same failure as `JobProfileRow.queuedAt`, which rendered 271 queued files as "0 menunggu" for the same reason. In this repo a hand-listed row shape plus an optional field is a silent drop waiting to happen; make the field required and let tsc find the constructors.

**What made that report slow was the embedding tier, and the cache that fixed it is a table** (`job_family_title_embed`, drizzle/0070). Matching needs one vector per job-profile NAME plus one per title the deterministic tiers could not place — measured here 280 + 462 = 742 texts — and `job_family_config`'s embedding source on this deployment is `nomic-remote`, a hosted gateway at **5.2s per 200-text call**. `embedTitles` chunked those 742 into four **sequential** calls, so the tab spent **18.5 seconds** embedding against a **0.35s** database phase. An in-process `Map` already existed and was doing its job — but a `Map` is per-process, so every restart, deploy and extra worker re-paid the full cost, and this is not a page anybody keeps warm. Cold-process end-to-end went **18465ms → 1273ms** with byte-identical output (matched 318 / unmatched candidates 22 / profiles 80 / positions 284); re-measure with `scripts/bench-job-profile-match.ts`, which stubs the Keycloak gate because the path is otherwise unreachable outside a browser session.

Four decisions in there are worth not undoing:

- **It caches VECTORS, not match decisions.** A decision is a function of the whole JD corpus, so importing one job profile would invalidate every row and buy back the 18s; a vector is a function of `(source, model, exact text)` alone, so a new JD costs exactly one embed call and needs no invalidation column, no fingerprint, and no `METHOD_VERSION` — the trap the career anchors hit twice.
- **`bytea` Float32 in the MAIN database, not `vector(768)` in the vector DB.** Nothing here does a nearest-neighbour search — the cosines are computed in JS against an in-memory corpus — so pgvector buys nothing and `VECTOR_DATABASE_URL`'s cross-instance caveat costs something. Float32 halves the read (442ms vs 1030ms for the full set) and its ~1e-6 error cannot decide anything at a 0.98 threshold. But it does mean a cached vector is **not** bit-identical to a fresh one, so `embedTitles` runs fresh vectors through the same quantization: without that, a title could land on either side of the threshold depending on whether this process had already embedded it, and the report would reshuffle between page loads — exactly what the AI tier's decision cache exists to prevent on its own side.
- **The remaining chunks run 3 at a time**, not sequentially. Concurrency is capped low on purpose: the ceiling is the gateway's, and this is a report, not a batch job.
- **Every cache failure degrades to a miss, and a write failure is logged.** A missing table costs what the page cost before the cache existed. Silence there would be the drizzle/0067 trap — a permanently failing write that looks transient and re-does the work forever.

One unrelated cost went with it: the AI tier committed its decisions with **one `INSERT` round-trip per title** inside the decision loop, so a full 150-title batch spent seconds on the wire after the LLM had already answered. It is now a single statement, deduped on `titleKey` first — two titles can normalize to one key, and Postgres refuses to update the same row twice in one `ON CONFLICT`.

**Struktur Posisi (the synced org chart) is DELETED** (2026-11, by request): the `/posisi/struktur` page, `components/job-profiles/position-explorer-panel.tsx` and its loader `getPositionHierarchySnapshot` (`lib/sync-actions.ts`) are gone. `/posisi/struktur`, `/job-profiles/struktur` and `/job-profiles?tab=hierarchy` now redirect to the Job Family map. The sync job that feeds `sync_position_hierarchy` ("Hierarki Jabatan" on Sinkronisasi) is untouched — the page was its only reader in the web app, but it is synced data and the job still runs.

**Job profile ingestion has a QUEUE, and it is a column of its own** (`sync_job_profiles.queued_at`, drizzle/0075). The "Dalam Proses" card could only ever read **1**: `processOneFile` marks exactly one row `status = 'processing'` and flips it to `completed` before touching the next file, and a file not yet reached has no row at all (first ingest) or still carries its previous `completed` row — so the backlog existed nowhere but in the scan loop's cursor. The number changed which file it referred to, never how many were left.

The obvious fix is the wrong one. **Marking the batch `status = 'pending'` up front would empty the job-profile corpus for the length of the run** — nine call sites select on `status = 'completed'` (job-family matching, `resolveJobProfileIdentifier`, `getJobProfileByPosition`, the scoring engine's career/technical corpus), and every one of them would simply find nothing and fall back, silently, for the hour a 280-file extraction takes. So `status` keeps meaning *the state of the extracted CONTENT* — the previous extraction stays valid and readable until the new one replaces it — and `queued_at` means *this file is waiting for (re)extraction*. A file being extracted right now is still in the queue; only a terminal state (`completed`/`failed`) clears it.

`syncJobProfiles` is therefore two phases: **plan** (scan, hash, decide skip-vs-extract for every file, write the queue) then **extract**. Planning costs what scanning already cost, because the old loop read and hashed every file too, including the ones it skipped; the buffer is deliberately not carried into phase 2, since holding a few hundred PDFs in memory to save one re-read is a bad trade against PDF→PNG plus a vision call. The skip decision is the exact De Morgan dual of `processOneFile`'s own guard — which stays as a safety net — so **which** files get extracted is unchanged. New and existing files enqueue in ONE statement (`INSERT … SELECT FROM UNNEST(…) ON CONFLICT (file_path) DO UPDATE SET queued_at = NOW()`): a file nobody has ingested is INSERTed as `pending` (it was never in the completed corpus, so nothing can regress), an existing one gains only `queued_at`. A full run resets the whole queue at its start — that is what clears a phantom backlog left by a run killed mid-extraction — while an `uploadsOnly` run clears per file, because it cannot see the rest of the corpus and must not wipe a concurrent full run's queue.

**Extraction retries, and the `temperature: 0` trap.** `extractJobProfile` had no retry at all: one malformed response and the row was `failed` for good. It is now wrapped in `extractWithRetries` (`JOB_PROFILE_EXTRACT_ATTEMPTS`, default 3; exponential backoff from `JOB_PROFILE_EXTRACT_BACKOFF_MS`, default 4s, jittered 0.5–1.5× so a failing batch does not retry in lock-step). Errors are deliberately **not** classified by message — everything that call throws is worth another attempt, and matching on error strings is a guess that silently stops retrying the moment a gateway rewords something. PDF→PNG conversion sits outside the wrapper, so a corrupt file costs one attempt rather than three.

**The retry only works because it varies the temperature, and that is the whole point.** `getModel` was a single cached `ChatOpenAI` at `temperature: 0`, so re-sending identical images returns identical tokens — a retry of a malformed-JSON failure reproduces the identical malformed JSON, at the cost of another multi-page vision call. The cache is now keyed by temperature: attempt 1 stays at 0 (so a normal extraction is reproducible), later attempts step up to a cap of 0.6. This matters because **every failure observed on this deployment is a `JSON.parse` SyntaxError** — 5 of ~58 during one run — not a transport error. Their break positions (2517, 2845, 4208, 6027, 7022) span the *same* range as successful `extracted_data` lengths (min 2512, median 4335, max 7224), which rules out the 4096-token `maxTokens` cap: a fixed output cap would truncate every document at roughly one length, not in proportion to each one. The output is ending early or losing a closer, per document.

**A parse failure now records what it actually saw.** The raw response was discarded, so `error_message` read `SyntaxError ... at position 2517` and the text was gone forever — which is why the question above had to be answered by inference. The thrown error now carries the total length, a ±120-char window around the break, and whether the break was at the END (output stopped early) or in the MIDDLE (malformed), because those have different fixes. Deliberately NOT done yet: raising `maxTokens`, or repairing the JSON by appending closers. The evidence does not yet support either, and the captured window is exactly what will settle it on the next failure — repairing brackets blind risks inventing a job profile.

**"Coba Lagi Semua" re-queues every `status = 'failed'` row** (`retryFailedJobProfiles` → `POST /api/sync/job-profiles/retry-failed`). It returns as soon as the batch is QUEUED, not when it finishes: each file is a multi-page vision call, so awaiting the batch would hold the HTTP request open for minutes and time out mid-run with the work still going — the queue is what makes that safe, since the page reads the backlog from the database and watches it drain. A row whose PDF is no longer on disk is answered immediately instead of being queued to fail again, and counted separately, because the fix there is a re-upload rather than another attempt. One bulk retry at a time (`retryAllInFlight`), and the `finally` dequeues the batch so a throw cannot leave a permanent phantom backlog.

**"Dalam Proses" counts documents with no usable extraction yet — NOT the whole queue.** The two are different during a force re-sync, which enqueues every file on disk: counting re-reads in that headline reported 234 in progress against 275 total with 255 already finished, which reads as broken arithmetic and made the card useless for the one question it answers ("how much is missing"). A queued file whose previous extraction still says `completed` already has content, is already counted under Selesai, and is readable right now — so it appears only as a subordinate "N baca ulang terjadwal". It is still real work (one vision call each), and the page's 10s poll deliberately DOES include re-reads, because a force re-sync is exactly when somebody sits watching the page. The badge says **Antre** for a queued file (a re-read keeps `status = 'completed'`, so without that arm a file waiting an hour renders as "Selesai"), and the page polls every 10s **only while the queue is non-empty** — the list is server-rendered, so it is stale the moment an extraction starts.

One connection nuance: `job_profile_embed` and the `kamus_kompetensi_*_embed` vector tables follow `VECTOR_DATABASE_URL` (`lib/db/vector-db.ts`), which falls back to `DATABASE_URL` but need not be the same instance. Anything that filters vectors by a non-vector table — tenant ownership, most obviously — must pass an id list rather than SQL-join across that boundary.

### Frontend structure

Next.js App Router with route groups: `app/(dashboard)/*` is the authenticated app shell (candidates, positions, scoring, analysis, governance, job-profiles, settings), `app/auth/signin` is the Keycloak sign-in page, `app/api/*` hosts NextAuth handlers plus thin proxy routes to sync-service/scoring-service. Server actions live in `lib/*-actions.ts` (one file per domain — e.g. `pulse-crud-actions.ts`, `job-profile-actions.ts`, `program-actions.ts`) rather than colocated with routes.

UI components: shadcn/ui ("new-york" style, Tailwind v4, no config file — see `components.json`) live in `components/ui/`; feature components are grouped by domain under `components/{analysis,governance,job-profiles,scoring,settings}/`. Path alias `@/*` maps to repo root (`tsconfig.json`).

**The menu is a registry, not a component.** `lib/navigation.ts` is the single source of every top-level route's href, label and RBAC permission — `SIDEBAR_GROUPS` (Alur Kerja / Data Referensi / Administrasi), the two CTAs (`SCORING_CTA`, `TALENT_POOL_CTA`) and the hub sections (`JOB_PROFILES_HUB` for Dokumen, `POSITION_HUB` for Posisi, `TALENT_POOL_HUB`) — plus `routeLabel(pathname)`. `components/sidebar-nav.tsx` only adds icons (an href→icon map) and `lib/activity-thread.ts`'s `detourLabel` reads the same table, because those two and each page's `DashboardHeader title=` used to be written independently and had drifted. The registry is deliberately client-safe (its only rbac dependency is `import type { Permission }`; `lib/rbac.ts` is `server-only`), so keep icons and server imports out of it. Adding a menu = adding a row there and an icon in the sidebar map; do not hand-write an href in a nav component.

**Tata Kelola is four sections, and each editor says where it applies.** `components/governance/governance-client.tsx` groups them as Aturan Penilaian (Program Penilaian · Instruksi & Model AI · Kesiapan & Pensiun) and Pemantauan (Riwayat Perubahan). "Instruksi & Model AI" is one block, "Prompt AHP + TOPSIS", listing only the allowlisted prompts (`ACTIVE_SCORING_PROMPT_KEYS` in `lib/scoring-prompt-keys.ts`); Konteks Bisnis and Umpan Balik AI were deleted with the AI Tournament. The Grade Levels tab was folded into the third section — the grade ladder is the reference the retirement thresholds are keyed on — and `parseGovernanceTab` still accepts the old `?tab=contexts|grades` values (`feedback` falls back to Program Penilaian). Each section header carries a scope badge (Company aktif vs semua Company) because programs and audit are tenant rows while prompts and both threshold files are app-wide, and "I changed Readiness in Mulia and MSO changed too" was a recurring question. The program picker is a chip row, not a second left column, and `ProgramDetailEditor` is keyed by template id with one sticky "Simpan program" bar: the per-section "Ubah" buttons only open editors, `dirty` compares state to the template, and Save is disabled when nothing changed. Switching sections writes `?tab=` with `history.replaceState`, so a refresh lands on the same section without re-running the page's eleven server reads.

**Dokumen and Posisi are two hubs of nested routes, not tabbed pages** (Data Referensi). They used to be ONE menu, "Profil Job", with five sections; it was split because the sections answer two different questions. **Dokumen** (`JOB_PROFILES_HUB`) is the documents and what is read straight off them: `/job-profiles` (Dokumen Job Profile), `/job-profiles/match` (Job Profile Match), `/job-profiles/kamus` (Kamus Kompetensi). **Posisi** (`POSITION_HUB`) is what is built from them about positions: `/posisi/job-family` (the Job Family map) only, since Struktur Posisi was deleted — so `HubChrome` renders the header and **no section strip** (it draws one only when a hub has more than one visible section); `/posisi` itself redirects to the map. ### Localization

Server action error messages and several UI labels are in Indonesian (e.g. `"Posisi sasaran tidak ditemukan."`) — match this convention for user-facing strings in `lib/*-actions.ts`; code identifiers, comments, and logs stay in English.

**"Aturan filter" is the one user-facing name for a program's eligibility rules.** It had four: *aturan kelayakan* (Talent Pool, candidate detail), *Aturan Filter Kelayakan* (governance, the run-configuration panel, and the scoring engine's own all-candidates-failed error), *aturan filter* (the create-program dialog and most of the docs) and a bare *aturan* (the editor's own buttons and placeholders) — so the thing the governance editor writes, the thing the Talent Pool page counts and the thing a failed run names were three different words for one `filterTree`, and a user searching the docs for the error they had just been shown found nothing. Everything now says *aturan filter*, title-cased only where it is a heading or a section name (`Aturan Filter`). The rename covers the UI strings, the audit summary in `updateTalentPoolFilterAction`, the engine's error, the `=== ATURAN FILTER ===` block in the AI prompt context and the three docs. Two references deliberately keep their old wording: both quote the text of the **removed** "Aturan filter tidak ditegakkan" banner, and renaming a string that no longer exists would misdescribe what was deleted. *Grup* still means a group; only the rule itself was renamed.

**Dates are the one thing deliberately NOT localised.** `lib/datetime.ts` is the only place this app turns a timestamp into text: `YYYY-MM-DD HH:mm` with a time, `YYYY-MM-DD` without, pinned to `Asia/Jakarta` — the business zone, not the viewer's, because these timestamps are evidence about when an assessment was made and two people reading one run must see one wall-clock. ISO ordering rather than `id-ID` because the app previously mixed `24/08/2026 18:04`, `24 Agu, 18.18`, `24 Agu 2026, 04.18` and `24 Agustus 2026` on adjacent screens; `24/08` versus `08/24` is unreadable without knowing which convention a component picked, and big-endian digits sort, never ambiguate, and are one width in every row. `formatHistoryDate` additionally folds the sync's year-9999 open-stint sentinel to `Sekarang` — five copies of that helper existed and disagreed. Don't add a formatter; add a function there. (scoring-service had a mirror, `src/datetime.ts`; its only reader was the deleted AI Tournament, so it went too — restore it from git rather than writing a new one if the service needs dates in text again.)

**The zone-less timestamp columns are the trap underneath that.** 55 columns are `timestamp without time zone` holding WIB wall-clock, because the database's `TimeZone` is `Asia/Bangkok` (+07) so `DEFAULT now()` stamps local time. node-postgres parses an offset-less value using the *reading process's* zone, so a UTC container read 11:04 WIB as `11:04Z` — an instant 7 hours late — and rendering that in Asia/Jakarta printed **18:04**. On a WIB developer machine the parse error and the render offset cancelled exactly, so this looked right in dev, was 7 hours wrong in the container, and logged nothing. `lib/db/pg-time.ts` (mirrored into both services' `src/db/`) pins the parse for OIDs 1114 and 1082 so a stored value means the same instant everywhere; a `date` becomes **UTC** midnight, not local, because that is the only choice under which both habits already in this repo agree — `lib/age.ts` reads local calendar fields off `birth_date`, exports slice `toISOString()`.

**The driver pin alone was NOT the fix, because Drizzle bypasses it.** drizzle-orm's node-postgres session passes a per-query `types` override returning TIMESTAMP/DATE/TIMESTAMPTZ as raw strings, so the global parsers never run for ORM queries; `PgTimestamp.mapFromDriverValue` then does `new Date(value + "+0000")` — it declares WIB wall-clock to be UTC, +7 on **every** host, which is why the audit trail showed 20:02 for a 13:02 run even on a WIB laptop. `lib/db/drizzle-time.ts` closes both directions: `mapFromDriverValue` is a prototype method, patched once globally; `mapToDriverValue` is a per-instance arrow field (`value.toISOString()` — UTC wall-clock into a naive column, unfixable by `TZ`, the source of 7.00h-skewed `updated_at` rows), so `installDrizzleTimeMappers(schema)` also walks the schema and replaces it on every naive-timestamp column. `timestamptz` columns are untouched on both sides. `toDate` in `lib/datetime.ts` additionally pins offset-less timestamp *strings* to +07:00, because `db.execute(sql``)` skips column mapping and hands formatters raw strings that `new Date()` would parse host-locally. Verify with `scripts/verify-drizzle-time.ts`, which must PASS under both the host TZ and `TZ=UTC`.

Reads are now host-independent; **raw-`pg` writes are not**, and that is why `TZ=Asia/Jakarta` is set on every service in `docker-compose.yml`. node-postgres serialises a JS Date in process-local time, so `updatedAt: new Date()` into a zone-less column stores UTC wall-clock in a UTC container — 7 hours behind the `now()`-written column beside it, in the same INSERT. `assertBusinessTimezone()` warns on startup rather than letting that stay silent; prefer a Postgres-side `now()` over `new Date()` for any new write to a zone-less column. Migrating all 55 columns to `timestamptz` is the better schema and a change of its own — the writers have to convert first.

**`lib/run-label.ts` is the coupling that bites when the format changes**, and it bit twice. `runLabelCore` strips scaffolding off a derived run's label — deltas from the front (`DELTA_SEGMENT`), date/timestamp stamps from the back (`STAMP_SEGMENT`) — so a re-run of a re-run collapses instead of nesting. Both patterns must cover **every shape the app has ever written**, not just the current one, because `scoring_runs.label` holds all of them:

| | shapes that must match |
|---|---|
| `STAMP_SEGMENT` | `2026-08-24 11:05` (derived tail) · `2026-08-24` (**base** label tail, from the wizard and `lib/scoring-engine.ts`) · `24/8/2026` (legacy `toLocaleDateString('id-ID')`, unpadded) · `3 Agu 2026, 13.49` (legacy) |
| `DELTA_SEGMENT` | `+2 kandidat` · `+2 kandidat (data terbaru)` · `−2 kandidat` (U+2212) · `tanding finalis` · `data terbaru` — every delta in `RERUN_MODES[*].delta`, the four legacy modes' included, since stored labels carry them — plus older `Re-scoring (+2 kandidat)` / `Re-ranking (−1 kandidat)` / `Run pool penuh (+2 kandidat)` |

Missing a shape fails two different ways and **neither throws**. A missed *stamp* duplicates: a base label already ends in a date, so the core carries it through and the derived run appends a second one — `… — ANALYST — 2026-08-24 — 2026-08-24 13:02`. A missed *delta* grows: the prefix stacks one per generation (`+1 kandidat — +1 kandidat (data terbaru) — …`), ~15–28 chars each, until the `varchar(255)` INSERT fails and surfaces as a **failed scoring run**. Both were live — the rerun-modes refactor changed the delta wording without updating the regex, and the ISO switch introduced a date-only base tail the stamp regex did not recognise. `assertDeltaSegmentCoversRerunModes(RERUN_MODES)` now ties the delta pattern to the mode table, and `scripts/audit-run-label-stamps.ts` asserts both against the real 183 labels — run it after touching either.

Generated labels put the stamp in **its own `RUN_LABEL_SEPARATOR` segment** for exactly this reason (`lib/position-bulk-actions.ts` was writing `Auto AHP 2026-08-24` as one segment, which no stripper can reach without parsing inside a segment and risking a legitimate name).

Two more traps. `compactRunLabel` in `lib/activity-thread.ts` used to slice its fallback out of the ISO string "so the server and the client cannot disagree"; slicing reads UTC fields, so it rendered 04:04 for an 11:04 run — a pinned formatter satisfies the same requirement correctly. And `new Date().toISOString().slice(0, 10)` is the same UTC-field bug wearing a different hat: it dated bulk-add and program-rescore run labels **a day early for the first seven hours of every WIB day**. Use `formatDate`. The one legitimate use of that idiom left is `shiftDay` in `lib/audit.ts`, which builds its Date with `Date.UTC` and reads it back in UTC — self-consistent by construction.

### Candidate soft delete

`candidates` rows are **tombstoned, never deleted** (`deleted_at` / `deleted_by` / `deleted_mode`, added in `drizzle/0045`). A real `DELETE` cascades into `analysis_results`, `position_picks` and `job_family_matches`, and leaves the candidate's uuid dangling inside `tournament_sessions.current_pool` / `pending_pool` (jsonb, no FK) — so removing one person silently rewrites every finished ranking they appeared in.

Two rules that are easy to break:

- **`idx_candidates_tenant_employee_id` must stay a TOTAL unique index.** `candidate-populate.ts` upserts with `ON CONFLICT (tenant_id, employee_id)`, which can only infer a total index. Making it partial (`WHERE deleted_at IS NULL`) makes that statement fail, and "fixing" it so it matches would make a resync INSERT a brand-new uuid for an NPK that already has a tombstone — the exact identity break the tombstone prevents.
- **`deleted_mode` decides whether a resync resurrects the row.** `'bulk'` (cleared from the Sinkronisasi page before a re-import) is cleared by the sync's `DO UPDATE`, so the candidate returns *with the same uuid*. `'manual'` (deleted one at a time from the Kandidat page) is preserved, otherwise the Monday 01:00 cron would overturn that decision every week.
- **The NPK is identity, and `updateCandidateAction` never writes it — but it must not silently DISCARD a changed one either.** `employeeId` was simply left out of the `.set()`, which was the right call (it is half of the total unique key the sync upserts on, and ~23 raw-SQL sites resolve a person through `LPAD(employee_id, 5, '0')`) made invisible: the form renders "ID Karyawan" as a **required editable field**, so retyping it reported "Kandidat berhasil diperbarui" over a value that never moved. A user who typed an NPK already belonging to somebody else read that as the collision being handled, when nothing had been checked at all. `assertNpkUnchanged` now rejects a changed NPK *before* any write, with the two cases separated because the user's next move differs — already taken (fix the input) versus free but frozen here (delete the candidate and let the sync recreate them). Comparison is on `npkIdentity`, which pads **numeric** ids to 5 so `370` and `00370` are one human: the unique index sees two distinct strings, and non-numeric ids are deliberately NOT padded because `LPAD` *truncates* past its length, which would fold `MUL-2024-001` and `MUL-2999-999` into one `MUL-2`. Tombstoned rows count as taken — that is the point of the index being total. The field is also `readOnly` on edit (`readOnly` still submits, `disabled` does not, so the server keeps its own check), and `CandidateFormDialog` now RENDERS the rejection: it used to `catch {}` with a bare comment, so the candidate **detail** page — which passes the server action straight through with no toast wrapper — showed nothing at all and the dialog just sat there.

Nothing filters tombstones automatically — Drizzle `relations()` are declared but never used, every query is an explicit select/join. Use `liveCandidate()` / `liveCandidateSql(alias)` from `lib/candidate-visibility.ts`, and note the three categories documented there: pools/lists and identity resolution **must** filter; history rendering (`analysis_results` enrichment, `position_picks` labels, audit strings) **must not**, or a finished ranking renders with holes. `scoring-service` reads the same DB and filters in its own raw SQL — if only the web app filtered, a tombstoned candidate would still get scored.

### Demo mode (`?mode=demo` / `?mode=asli`)

A second app mode for demonstrations (docs/mode-demo.md). It has **no UI control and no indicator, on purpose**: `proxy.ts` turns the keyword on any page URL into the session cookie `pulse_mode` and 307s to the clean URL. A deployment may change what an un-switched browser gets: `PULSE_DEFAULT_MODE=demo` (runtime env, no rebuild) makes demo the default and the cookie then stores only a departure from it (`pulse_mode=real` for `?mode=asli`); `PULSE_MODE_LOCKED=1` ignores the keyword so the default cannot be left by URL. Both rules live in `resolveAppMode` / `deploymentModeConfig` (`lib/app-mode-shared.ts`), read by `proxy.ts` and the server alike. Server code reads it with `getAppMode()` / `isDemoMode()` (`lib/app-mode.ts`, `'real'` outside a request whatever the default — a script must never pick up demo mode from how the web container was configured); components with `useIsDemoMode()` / `useIdentifierDisplay()` (`components/app-mode-provider.tsx`); pure client helpers that run in handlers (copy-text builders, exporters) with `clientIdentifierDisplay()` (`lib/app-mode-client.ts`), which the provider sets in the browser only — never set it on the server, where a module-level value would be shared by every request.

**Candidates are never written in demo mode.** Edit stores the form as a sealed copy in `candidates_dupp` (drizzle/0093); Turnoff/Reload flip `candidate_demo_states` (no row = OFF, so everyone starts off); Reload deletes the copy and turns the candidate on. Readers apply the copy with `forCurrentMode(rows, idOf, { onlyOn })` (`lib/demo/store.ts`) — `onlyOn: true` for every eligibility/pool/Talent Pool/Talent Mapping/scoring reader (an OFF candidate is as if deleted), `false` for the Kandidat list (it must show OFF people so they can be switched on) and for history — and they apply it BEFORE `withEffectiveHav`, which in demo mode drops real placements only for candidates whose copy EDITS the HAV (scoring-service mirror: `ignorePlacementsFor: havEditedIds(...)`).

**A demo candidate is the fields EDITED in demo mode plus every other field LIVE — never a snapshot of the form.** The copy carries `editedFields`; `loadDemoCopies` (both deployables) returns it already RESOLVED against the real row now (`resolveDemoCopy`, `lib/demo/fields.ts`, mirrored in `scoring-service/src/demo-overlay.ts`), and both row overlays write only edited fields. The form decides what was edited by comparing what it submits with what it rendered on opening (captured from the form DOM itself, so formatting cannot differ) and sends `editedFields`; a field stays edited until Reload, and a request without the list counts as editing everything (an old tab). The snapshot this replaced froze the HAV: the form shows the HAV IN FORCE, so a candidate whose PA was edited kept the HAV the old PA produced, in the filter, the Talent Pool, the map and both engines. Now an untouched HAV resolves as usual (placement › upload › formula over the merged PA/BA), and the Talent Mapping "automatic" square UN-EDITS the HAV rather than writing null. Copies saved before `editedFields` existed infer it — a field differing from the real value, except that a HAV equal to the real upload or the real formula is not an edit (that is the snapshot of the HAV in force). Competencies: null = keep the real ones, which is now what an untouched list stores. scoring-service also drops candidates switched OFF since the session was built (queued sessions, the orphan sweeper) at hydration, like a tombstone — except candidates carried from a parent run. The filter pickers in demo mode offer the values of ON candidates as the rules will judge them. Pinned by `tests/demo/demo-merge.test.ts` (incl. web/service parity). **The overlay never substitutes `employeeId`**: every NPK join and incumbent exclusion must keep meaning the real person; the NPK typed into a copy lives only in the copy. scoring-service overlays the copy itself for demo sessions (`scoring-service/src/demo-overlay.ts`, keep its field list in step with `lib/demo/fields.ts`). Any write reachable in demo mode is one of three things — a demo action (`lib/demo/candidate-demo-actions.ts`), an edit of the copy (`patchDemoCopy`: Talent Mapping move), or refused (`refuseInDemoMode()` / `'Aksi ini tidak tersedia.'`) — decide which when adding one. Governance and settings are deliberately NOT sandboxed.

**Runs, sessions and picks carry `is_demo`, and every listing and by-id lookup scopes by it** (`runsOfCurrentMode()`, `sessionsOfCurrentMode()`, `picksOfCurrentMode()`, `isDemoSql(alias)` in `lib/demo/run-mode.ts`): demo mode never shows a real run (it may hold candidates that are OFF) and real mode never shows a demo one. The picks unique key includes `is_demo`, or a demo pick of someone chosen for real would upsert the real decision. A write that touches only mode-scoped rows passes `logAudit({ demoScoped: true })`, so demo actions stay out of the shared trail real mode reads.

**Masking — no NPK, position code, competency code or photo anywhere in demo mode.** Shapes that feed many screens are masked at the server (`maskProfileForDemo`, holders, lookups, Talent Pool/Mapping rows, wizard preview — incumbency comes back as `incumbent` by candidate id because masked NPKs all compare equal); single displays mask with `useIdentifierDisplay().npk()/.code()`; the engine writes demo-safe provenance, and a demo run writes no AI narrative at all (the template one stands). **Files are the exception to the fixed mark**: the trace XLSX and snapshot JSON use stable pseudonyms (`lib/demo/pseudonymize.ts`, `NPK-0001` / `KODE-001`) because the workbook's formulas compare and VLOOKUP on those values — one shared `•••` would make every code equal every other (verified: a demo workbook recalculates to SEMUA COCOK). Pinned by `pnpm test:demo`. Known limitation: the Talent Mapping queue's BA/PA evidence reads synced data, not the copy — except that a candidate whose BA was edited in demo mode shows the edited value alone, not the real dated history beside it.

**Candidate names leave the server as unique INITIALS, and that is a data transform, not a display one** (docs/mode-demo.md § Nama kandidat). `demoScrub()` (`lib/demo/names.ts`) is the one function every name-bearing boundary calls: page props, server-action returns (most wrapped mechanically — the original renamed `…Impl`, the export returning `demoScrub(await …Impl(...args))` — so every return path is covered), chat history, and the trace bundle (`lib/run-trace/load.ts`). The rule is `lib/demo/initials.ts` (first letter of every word; a later candidate with identical initials takes the 2nd, then 3rd… letter of the LAST word as its last initial; numbered when exhausted), assigned over EVERY candidate row — all tenants, tombstones, ON and OFF — oldest first, from the name IN FORCE (the `candidates_dupp` copy's when there is one; the real name stays an alias to the same initials). `lib/demo/name-scrub.ts` recognises names by id first (`id` / `candidateId` objects — namesakes stay apart, a renamed snapshot is still caught, and that row's `email` is masked), then multi-word names anywhere, then one-word names only with context (the payload references that candidate, or the caller passes `contextCandidateIds`) and capitalised, never inside seat fields (`STRUCTURAL_KEYS`); business-unit names are a stop list. Things that are easy to break: **apply it on the way OUT, never before a write** — `runJobProfileMatchAction` stores its report first; the Kandidat demo Edit form is safe only because it records just the fields that CHANGED from what it rendered, so the untouched initials never become an edited name. **A new action that returns candidates, runs, picks or narratives must be wrapped**, or demo mode leaks names and nothing fails. The Kandidat list and the re-run search match the initials (`demoInitialsById()`), so a real name typed into the box finds nobody. Verify against `pnpm build && pnpm start`: `pnpm dev` ships awaited values as React debug info and leaks real names in the payload regardless.

**Job profile content and the kamus are cut server-side in demo mode** (`lib/demo/text-mask.ts` rules, `lib/demo/content.ts` applied in `getJobProfilesAction`, `getJobProfileByIdAction`, `suggestJobProfileForSelectionAction`, `getRestructureSampleAction`, the Job Family topic/distance actions, and `listKamusCompetencies`): the named job-profile sections keep the first three words of every point (a point of ≤3 words keeps one word fewer, so it is never whole); kamus descriptions and level bullets keep `floor(n/5)` words at each end. The placeholder is `▒▒▒▒`, NOT `•`, because `toStringList` and the kamus `bulletize` split on `•`. The raw JSON tab is emptied and "Salin JSON" disabled on screen. Competencies, qualifications and identity stay intact — the position form copies them out of a job profile.

### Source-database settings & encryption

`DB_MPMDS_*` / `DB_MPMHRGA_*` are now a *fallback*: an active row in `sync_source_connections` (written by the web app under `sync.manage`, never by sync-service — that service has no auth) wins. `sync-service/src/db/mssql.ts` resolves its pool config **per connect**; it must never go back to module-level `const` snapshots, because that failure mode is invisible (the row updates, the API answers 200, and the service keeps connecting to the old server forever, including after a reconnect).

The "Koneksi Source Database" card and the candidate-data card (pool clearing) on `/settings/sync` are HIDDEN, not deleted (`SHOW_SOURCE_CONNECTIONS` / `SHOW_CANDIDATE_MAINTENANCE` in `app/(dashboard)/settings/sync/page.tsx`); a stored connection row keeps winning.

Stored passwords are encrypted with AES-256-GCM envelope encryption (`lib/crypto/envelope.ts`, mirrored for decryption only in `sync-service/src/services/crypto.ts` — the `v1:<iv>:<tag>:<ct>` wire format is the contract between them).

**Key custody is a file**, at `PULSE_MASTER_KEY_FILE` (default `secrets/master.key`, bind-mounted rw into web and ro into sync). The Keamanan page (`/settings/security`) generates and rotates the key inside it; `lib/crypto/master-key-file.ts` owns all reads and writes. Both the web app and sync-service read that file and unwrap the DEK themselves via `ensureUnlocked()`, so a restart **self-heals** — which is the only reason the Monday 01:00 cron can touch an encrypted column at all. `PULSE_MASTER_KEY` (inline base64) is supported for env-injected secrets but cannot be generated or rotated from the UI.

The threat model this buys: someone with **database** access cannot read the protected columns, because the key is not in the database. Someone with **filesystem** access to the container can. Keep the mount minimal.

Two invariants worth not breaking: rotation re-wraps the *same* DEK, so nothing is re-encrypted and processes already holding the DEK stay valid — and it writes the **database row first, then the file**, rolling the row back if the file write fails, because a new key on disk that the DB cannot match would lock the app out of its own data. `lock()` sets a sticky in-memory flag; without it the next request would silently re-read the file and undo the operator's action.

Values not in the `v1:` format pass through unchanged, which is what lets a column be switched on without a backfill. Write through `encryptIfEnabled()` (`lib/crypto/key-store.ts`), never `encryptValue()` directly — it encodes the three-state rule: **plaintext** when encryption was never initialised (so installs that never opted in keep working), **ciphertext** when unlocked, and a **hard error** when initialised-but-locked. Falling back to plaintext in that last case is the one option that must never be taken: the column would silently hold a mix the operator believes is uniformly protected.

**Encrypted today:** `sync_source_connections.password_encrypted`, `chat_messages.content`, `talent_mapping_placements.{quadrant, baseline_quadrant, justification}`, the `'hav16'` rows' `talent_audit_logs.{old_quadrant, new_quadrant, baseline_quadrant, justification_reason}`, and the 19 candidate columns in `CANDIDATE_ENCRYPTED_KEYS` (`lib/candidate-crypto.ts`) — including both MCU note columns.

Only the first two are written by human-driven flows alone. The candidate columns are written by the **Monday 01:00 cron**, which works only because `resolveWriteMode()` auto-unlocks from the master key file first, so a restarted container encrypts instead of throwing — the self-healing described above is what makes an unattended encrypted write possible at all. It also fixes the failure mode: locked-but-initialised **refuses** rather than falling back to plaintext, because a column the operator believes is uniformly protected must never silently hold a mix.

The position page's **AI Assistant tab is HIDDEN, not deleted** (`AI_ASSISTANT_TAB_ENABLED = false` in `lib/position-result-tabs.ts`, read by `PositionDetailTabs`; the same module holds the list of `?tab=` ids `PositionRunSection` parses, retired ids via `RESULT_TAB_ALIASES` — pinned by `tests/scoring/result-tabs-and-menus.test.ts`): no trigger, `?tab=ai-assistant` opens Kandidat, and `AskAiProvider` gets `enabled={false}` so every "Tanya AI" chip on the derivation panels disappears with it — a button that switched to a tab nobody can see would strand the reader. Flip the flag to bring all of it back. When it is on, the chat panel can **export a conversation to PDF / .docx / .xlsx** (`lib/chat-export.ts`, rendering the block model in `lib/chat-transcript.ts`; menu at `components/analysis/chat-export-menu.tsx`). It runs entirely in the browser from the history the panel already decrypted, so it adds no server surface and no second copy of the permission rules — but it does put that prose, about named people, into a file outside the app's custody, which is why the document names the run it belongs to and labels any message that came back locked instead of printing the placeholder as if the assistant had said it. Two deliberate limits: a question sent from a derivation panel is recorded as its chip (which data, whose) and **not** its few-hundred-line payload, matching what the chat itself shows; and Word gets real OOXML via `docx` rather than HTML under a `.doc` name, because the latter makes Word warn on every open and save.

**What cannot be encrypted, and why** — `employee_id`/NPK is the join key across ~23 raw-SQL sites (usually via `LPAD(...,5,'0')`, with the two sides padded differently); `name` is searched with `ILIKE` and sorted on; `mcu_status`, `warning_level`, `education_level_rank` and `hav_quadrant` drive candidate derivation and filter rules in SQL; and candidate data is sent in plaintext to Gemini during scoring by design. Encrypting any of those breaks the product rather than protecting it. Roughly 73% of DB access in this repo is hand-written SQL across three deployables with no shared data-access layer, so there is no chokepoint for transparent column crypto — each additional encrypted column is a deliberate, audited change.


## Re-run scoring — aturan desain (sejak penyederhanaan mode)
- Hanya SATU mode re-run yang boleh dibuat: 'incremental_add', label UI "Tambah Kandidat Pembanding". Nilai di DB tetap 'incremental_add'.
- Prinsip: run turunan identik dengan induknya KECUALI himpunan kandidat. Yang dibekukan dari induk: enam skor aspek dan baseRaw kandidat lama, matriks AHP dan bobot akhir setelah pembagian ulang (Pers. 2.12), himpunan kriteria aktif, program/posisi/rentang level/aturan filter, jangkar kalibrasi, dan tanggal acuan penilaian. Yang dihitung baru hanya enam aspek kandidat yang belum ada di pool induk.
- Mode refresh_add, exclude, finalists_rematch, refresh_full TIDAK boleh dibuat lagi. Run lama ber-mode itu tetap harus terbaca, tampil di pohon run, dan bisa dibuka. Jangan hapus, ubah, atau migrasikan baris run lama.
- Re-run hanya untuk run AHP+TOPSIS. Metode AI Tournament (LLM) sudah dihapus seluruhnya (drizzle/0097).
- Data terbaru atau konfigurasi baru = root baru (wizard atau "Scoring Ulang" program), bukan child.
- Penjelasan selisih antar run dihitung deterministik, tanpa LLM.
- **Isi daftar hasil run turunan (FR-RR-09):** gabungan tanpa duplikasi dari N besar menurut peringkat baru (N = jumlah finalis run induk, tidak bertambah karena kandidat pembanding), semua finalis run induk, dan semua kandidat pembanding yang diterima; diurutkan menurut peringkat baru, setiap baris menampilkan peringkat pool penuhnya dan penanda "Kandidat pembanding", "Baru masuk N besar", atau "Keluar dari N besar". Kandidat yang tidak diminta tidak boleh muncul hanya karena kuota bertambah.
- **Basis posisi dibekukan (FR-RR-07):** kandidat pembanding dinilai terhadap basis posisi run induk — job profile, acuan kompetensi, syarat pendidikan, dan dokumen target karier — yang disimpan sebagai nilai (bukan ID) di `run_info.frozen.positionBasis` saat run root dibuat. Bila induk tidak menyimpannya, pakai nilai saat ini, tandai `live_fallback` per butir, dan tampilkan di banner run turunan dan halaman perbandingan. Pembekuan hanya mengganti sumber masukan; rumus enam kriteria dan pipeline embedding tidak boleh diubah untuk itu.
- **Kategori aturan bagi kandidat pembanding (Tabel 2.4):** Rejected ditolak beserta aturannya; Excluded (grade di luar rentang) hanya masuk setelah konfirmasi per kandidat dan selalu bertanda "Di luar rentang grade"; Reconsidered dinilai seperti biasa.

**Invarian yang mengikat seluruh fitur re-run dan perbandingan:**

- **I-1 Kekekalan run selesai.** Setelah berstatus completed, angka hasil, snapshot konfigurasi, dan keanggotaan pool sebuah run tidak boleh berubah oleh aksi apa pun (tata kelola, sinkronisasi, run anak, penandaan, keputusan forum). Catatan baru hanya boleh masuk ke tabel terpisah dengan pelaku, waktu, dan alasan. Dijaga trigger drizzle/0087; engine menulis `completed` paling akhir.
- **I-2 Pembekuan.** Run turunan membaca konfigurasinya dari snapshot induk; yang dihitung baru hanya enam aspek kandidat yang belum ada di pool induk, terhadap basis posisi induk.
- **I-3 Asal nilai.** Setiap butir snapshot punya label asal — `root_snapshot`, `frozen_parent`, `live`, `live_fallback`, `default` (atau tidak tersimpan) — dan label itu tampil di UI dalam bahasa pengguna, tidak pernah sebagai nama teknis.
- **I-4 Keterulangan.** TOPSIS yang dihitung ulang dari data tersimpan sebuah run menghasilkan kecocokan dan peringkat yang sama dengan yang tersimpan (|Δ| ≤ 1e-9, peringkat identik).
- **I-5 Satu posisi.** Perbandingan hanya antara run dengan tenant dan posisi target yang sama; ditolak di server (`comparabilityError`).
- **I-6 Kejujuran.** Apa pun yang tidak beku, tidak tersimpan, atau berasal dari model bahasa ditandai demikian di UI. Tidak ada fallback diam-diam; dua nilai yang sama-sama tidak tersimpan berstatus "Tidak tercatat", bukan "Sama".
- **I-7 Satu implementasi rumus.** Perbandingan, keterulangan, dan atribusi memakai fungsi TOPSIS scoring-service yang sama (diimpor langsung). Salinan rumus dilarang; satu-satunya pengecualian adalah oracle di tes.

Status setiap kebutuhan dan cara verifikasinya: `docs/rerun-requirements-audit.md` §6. Implementasinya diringkas di bagian "Re-running a finished run is ONE mode" dan "Any two runs of one position compare 1:1" di atas.
